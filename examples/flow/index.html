Most of what an app does is derive one view from another — a filtered list, a running count, a grouping — and keep it current as the data moves. Do that naively and you recompute everything on every change. Do it by hand and you drown in delta-stream plumbing. There is a third way: write the derivation you actually mean, and let the change — only the change — flow through it.

01

Everything is a derived view

Look at almost any screen and you are looking at derivations. The orders table is the base. Active orders is that table, filtered. Orders per region is the active set, grouped and counted. Average value is an aggregate over the whole. Each is a view defined in terms of another — and each has to stay right as orders are added, toggled, and removed.

Below is exactly that: a base table on the left of the page as a running history of changes, and on the right the derived views built from it. Add a change, toggle a flag, remove a row. Every derived view stays correct — and, as we'll see, for the price of the change, not the table. Scrub the change history to step back through how each view got where it is.

You wrote four one-line derivations. You did not write a single line that handles a change. That gap — between what you declare and what you'd otherwise have to maintain by hand — is the whole subject of this essay.

02

A derived view stays live

orders.filter(o => o.active) reads like a one-off: run the filter, get a list. But the list it returns is not a snapshot — it is a live view that the runtime keeps in step with orders. Add an active order and it appears in active; toggle one off and it leaves. You never re-run the filter; the view simply stays true.

Scrub the change history and watch it track. The membership of active isn't stored anywhere you manage — it follows from the same changes the base table sees, applied through the rule you declared once. The view you wrote is the thing that's maintained. 

const orders = $([…])
const active = orders.filter(o => o.active)   // a live view, not a one-off
// read `active` any time — it is always the current subset. You wrote the
// relationship; the runtime keeps it true as `orders` changes.
03

The cost is the change, not the table

Here is where the naive version falls down. When one order changes, the obvious way to keep active, perRegion, and avg correct is to re-derive them — re-scan every row. That's O(N) work for a one-row change, and it grows with the table: ten times the data, ten times the cost, on every single change.

The runtime doesn't do that. A change carries enough to update each view in place — flip one membership, adjust one bucket, nudge one running total. The work is proportional to the change, O(Δ), and it does not grow with N at all.

Before you scale it: as the table gets bigger, what happens to the cost of handling one change — for the naive recompute, and for the runtime? Place your bet, then drag the table size up.

04

A change reaches only the views that read it

The change is cheap for a second reason: it doesn't disturb every view — only the ones that read what changed. Toggle a row's active flag and membership shifts, so active and the per-region count both move — but the average never stirs, because no value changed. Bump a row's value and the average updates, yet the per-region count sits still: a tally of how many rows fall in each region never reads a value.

This isn't asserted; it's measured. Each change carries a dot for every derived view it actually moved — taken by comparing each view's output the instant before and after. Hover or scrub a change to light them, and notice how each kind moves a different, small handful.

That's what keeps the model composable. Add a tenth derived view and the nine others don't slow down, because a change they don't read never reaches them. The cost of a change is its size times the number of views that care — both small, neither N.

05

One primitive, composed

There is really only one primitive here — a view derived from another — and it composes without limit. A derived view is itself a perfectly good base for the next derivation. perRegion isn't built on the raw table; it's built on active: active.length(o => o.region). A derivation of a derivation, kept live exactly the same way.

And the chaining is real all the way down: when a change moves a row in or out of active, that movement is itself the change perRegion reads — incrementing one bucket, decrementing another. Watch one change to orders turn into the change active hands onward:

Compose these and you get leaderboards, histograms, pivots — non-trivial structures, each maintained by the same one step, none of them ever re-scanning. You declare the relationships; you never write the propagation. 

const active    = orders.filter(o => o.active)
const perRegion = active.length(o => o.region)   // a derivation of a derivation
// {north: 7, south: 9, east: 6, west: 8} — one bucket moves per relevant change.
06

You never touch a delta

Everything in §3 and §4 — the small change, threaded only through the views that read it — is happening under the floor. You can see it on the left, as the change history. But notice what your code looks like: it is the derivations, and nothing else. You never wrote an onInsert, never diffed two arrays, never reasoned about a stream of deltas over time.

That last part is the trap the other fast option springs. To make a recompute incremental by hand, you start handling change events — and then your derived-of-derived views are change-streams of change-streams, and the logic you actually care about is buried in plumbing. The deltas should be the runtime's problem, not your program's.

Both end up doing the minimal, incremental work. Only one of them is the code you'd want to read in six months. That's the whole pitch: the readability of recompute, the cost of hand-tuned deltas, and none of the bookkeeping.

07

The last derivation is the DOM

The screen is just the last view in the chain. render(el, orders, …) is not special — it's one more sink reading the same changes. And because each change names exactly what moved and by which key, it maps to one minimal DOM instruction: an insert is a single appendChild; a field update is a single text write to one node — the row itself never re-renders. There is no virtual DOM and no diff to compute, because there is nothing to discover: the change already said what to do.

A count in memory, a bucket in a histogram, a row on the page — the same derived view, maintained the same way, pointed at three different sinks. The framework doesn't know what a div is. It knows what a change is. 

// Three sinks, one set of changes.
orders.tap(change => console.log(change))      // into a console
orders.connect(myArray)                          // into an array
render(el, HTML.ul(orders, (li, row) => …))     // into the DOM
08

Best of both worlds

The pieces are old — incremental view maintenance, dataflow. What's new is the price: a library you drop into one page, a few kilobytes, that lets you write views the way you'd write business logic and pays only for the change. Once a derived view costs the change rather than the table, a lot stops being hard. Local-first apps keep derived state live off a change feed instead of round-tripping a server per query. A live dashboard updates in place instead of choosing between freshness and frame rate. An edge function hands a client a view and a stream of changes and lets it stay current without polling.

Build your own chain off the table above and watch it keep up. Then read how the operators compose in the reference docs, or see them under load in the examples. The idea is the one table and its derivations: you say what each view is, and the change does the rest.
