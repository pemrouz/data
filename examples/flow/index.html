What is a materialized view,
and why does it matter

Most code treats data as a thing you fetch, compute, and throw away. A reactive view inverts that: the answer to your query stays alive, and the runtime maintains it as the underlying data changes. This is what that means in practice — and what the pieces of a real implementation look like.

data · open source · MIT

01

The setup

Picture the simplest query: how many orders are active. In the way most apps are written, you read the orders list, run a filter, count what comes back, and write the number to the page. When something changes — a new order, a toggled flag — you do the whole thing again. Fetch, compute, throw away. Repeat.

This works, but it's wasteful. The answer to how many are active is a small integer, and it changes by at most one when a single row flips. Yet you've recomputed it as though nothing was known a moment before.

A reactive view inverts that. The answer is something the runtime keeps alive — a materialized view that exists between observations and is maintained as the data underneath shifts. You declare the relationship once; the runtime does the bookkeeping.

02

A view is a query that lives

Write $(orders).filter(o => o.active) and the framework doesn't run the filter. It builds a small object — an index — whose contents track which rows pass the predicate. The first observation populates it. Every subsequent change to orders updates the index in place: when a row's active flips to true, the runtime pushes one enter event downstream; when it flips back, one leave.

The filter itself never re-scans. The work each change costs is proportional to the size of the change, not the size of the dataset. Click any row below to flip its active flag and watch the filtered view update in place. 

const orders = $([{ id: 1, active: true, value: 87 }, …])
const active = orders.filter(o => o.active)
// `active` is now a live view. Reading it is free; mutating
// `orders` keeps it correct.
03

The cost of a change is the size of the change, not the size of the dataset

This is the central claim, and it has a name: incremental view maintenance. If your data has N rows and one row changes, the cost to update every downstream view should be O(Δ), not O(N).

In practice, a small constant amount of work happens at each operator the change passes through. A filter does one membership decision; a counter does one increment; a sum does one addition or subtraction. The cost scales with the path the change walks, not with what sits upstream.

Scale the dataset below and insert a row. The work-per-insert stays flat as N grows by three orders of magnitude. A naive recompute would scale linearly.

04

Selectivity: changes walk only the edges they need

If a single change costs O(Δ), what determines Δ? The dependency graph. Each operator is a node; each derives-from relationship is an edge. When you mutate a field, the change propagates through operators that read that field — and not through the ones that don't.

Below is a small graph: $(orders) feeds filter(o => o.active), which in turn feeds length() and sum('value'). Separately, avg('value') derives directly from the source.

The pulse on each tick traces the actual path the change walked. Toggling active lights filter → length and filter → sum, but never touches avg (it doesn't depend on active). Bumping value wakes avg and sum — but filter and length stay dim because membership didn't change.

This is what people mean when they call reactive systems sparse: propagation is local. It's also what makes the model composable. Adding another operator to the graph doesn't slow anything else down, because nothing else is on its path.

05

Composition: pipelines are graphs of small invariants

A complex pipeline is a sequence of operators where each holds a one-sentence contract. filter says: I am the subset of rows satisfying this predicate. group says: I am the partition of rows by this key. length says: I am the cardinality of my upstream. Compose them and you get an expression that maintains a non-trivial derived structure — a leaderboard, a histogram, a pivot — with the same incremental guarantee at every step.

You don't write the propagation. You don't say when a row enters the filter, increment the group's counter. You declare the relationships, and the runtime walks them. 

// One expression. The runtime maintains the whole chain.
const perRegion = orders.length(o => o.active ? o.region : null)
// {north: 7, south: 9, east: 6, west: 8} — updates in place.
06

The log is the source of truth; state is the fold

Step back from the operators for a moment and look at what's actually flowing between them. It isn't state. It's a sequence of small records — insert this row, update this field, remove this key — each one a self-describing claim about a single change.

Every operator in the graph speaks this same vocabulary. The source emits records when you mutate it. filter consumes them and emits new records (the rows that pass). length consumes those and emits an updated count. The propagation pulse from §4 is, concretely, a record threading through the graph.

This is the same insight Jay Kreps put at the centre of his essay on the log: the log of changes is the system of record, and any piece of state is just a fold over the log up to now. Replay the log from the beginning into the same fold and you reconstruct the same state. Subscribe a new consumer to the log and it can catch up the same way.

Below: a live view of the records emitted by mutating orders. Each click pushes one record onto the log; the panel on the right is state = log.reduce(apply, []) — literally that fold, computed on the spot. The records are what's real; the state is a window into the most-recent value of the fold.

07

The DOM is another sink

The framework doesn't know what a div is. It knows what a change is. Connecting a render(...) call is no different in shape from proxy.tap(fn) or proxy.connect(arr) — each is a sink that receives the same change records and chooses what to do with them.

The DOM happens to be a sink that translates inserts to appendChild, removes to remove, and updates to text or attribute writes. That's it. There's no virtual DOM, no diff, no reconciliation pass — the change record already says what changed, by which key, so the right node is patched directly. 

// Three sinks, one model.

proxy.tap(change => console.log(change))      // log every change
proxy.connect(myArray)                          // mirror into an array
render(el, HTML.ul(proxy, (li, row) => ...))   // paint into the DOM

The same model that maintains a number in memory maintains a row in the DOM.

08

Why this matters

The pieces are old — incremental view maintenance, dataflow graphs, log-structured propagation. What's new is the cost. A library you can drop into a single page can give you a database's worth of materialized-view machinery for the dozens-of-kilobytes of code it takes to express it. Local-first apps don't need a server round-trip per query. Live dashboards don't have to choose between freshness and frame rate. Edge functions can hand a client a view and a change feed and let it stay current without polling.

This library is one such piece. The reference docs explain how the operators compose; the examples show them under load. The idea, though, is the one above: you declare what you want to know, and the runtime keeps the answer ready.
