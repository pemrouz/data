# §02 The operator surface — REAL (variant b, the pick)

## What is real now
- **The feed.** `trades = $({ t1 … t14 })` on the page's own runtime (`api.$`, imported from `../engine.js`). A scripted writer issues ONE real write per ~110 ms through the public write path — `trades.get(k).set('px' | 'qty', next)` random walks, an occasional `trades.set('t15', row)` add and `trades.get(k).remove()` (the row count wanders 12–16). The writer is the synthetic INPUT; every printed figure after it is the engine's output.
- **The feed line** prints from `trades.sink({ apply(batch) })`: `rowCount()` (runtime), the CommitBatch's `seq` (runtime), and its first `RowDelta` rendered as `update t7 .px 187.70 → 187.78` / `add t15 { … }` / `remove t3` — prev/next are `leafAt(prev|row, path)` of the real delta (runtime). ⏸ pause / ▶ stream stops and restarts the writer; the writer also pauses while the variant is hidden, off-screen (IntersectionObserver ±160 px) or the tab is hidden; under `prefers-reduced-motion` it starts paused.
- **The four cards + 33 chips** come from `gen/manifest.json` (`operators` → category; **build** tier): the four counts (10 · 7 · 13 · 3), the lede's "All 33", the foot's "33 operators in 4 categories". If the fetch fails the same registry is read from `api.exportContract()` and attested `runtime`. Chip order within a card is curated; membership is the manifest's.
- **Every chain is built.** The lede says "All 33 below run live off one shared feed", so they do: the first time the section nears the viewport (IntersectionObserver, 600 px) every chip's chain is built on `trades` (33 nodes on ~14 rows — a millisecond; before this only the picked chip's chain existed) and stays live for the page's life; the panel paints the selected one.
- **The shared panel** paints the selected chip's REAL view on the feed, from that view's own subscription: collection views via `view.sink({ init, apply })` (the batch's update deltas drive the per-cell flash — presentation of a real delta), scalars via `view.connect({}, r => …)` (the v2 record profile: initial value, then one record per change), `tap` via its own side effect. Row counts are `view.rowCount()`; rows/order come from `view.each` (rank order for az/za/top/limit/reverse); bucket/group/distinct/keys contents from `view[value]`. Every row element, count, scalar, nudge and bound label is stamped `data-attested="runtime"`. The between chip has a real control: two sliders write `bounds.get('px').update([lo, hi])` — one visitor write; the engine then queues the re-bounding as the next commit (clause 5), so a drag costs two commits — and the view re-selects only the rows that crossed.
- **The chains, as printed in each signature:** `filter` · `map` · `gt/lt/gte/lte` · `between('px', bounds.get('px'))` · `buys.intersect/union/except(large)` · `sum('qty')` · `avg('px')` · `length()` · `group(t => t.sym)` · `length(t => t.sym)` · `some/every` · `az('px')` · `buys.za('qty', 5)` · `map(t => t.qty * t.px).top(3)` · `limit(4)` · `reverse()` · `max/min('px')` · `reduce(add, remove, 0)` · `distinct(t => t.sym)` · `to(v => Object.keys(v).length)` · `quantile('px', 0.9)` · `percentile('px', 90)` · `median('px')` · `tap(c => log(c))` · `keys()` · `values()`. Every shape was verified against the engine in Node before wiring (a scratch script over `api/index.ts`).
- **The cost word** per operator (`O(Δ)`, `O(Δ log n)`, `O(n)`, `O(1)`) is a CLASS, marked `data-literal`.

## Two places the engine corrected the plan (say so, per REAL.md)
- `lengthBuckets` is a registry operator but NOT a reserved handle name, so `trades.lengthBuckets(fn)` is not callable; its public spelling is `trades.length(fn)` (api/index.ts dispatches the function form to the registered `lengthBuckets`). The `lengthBuckets` chip therefore shows `trades.length(t => t.sym)` and says so; the `length` chip shows the count scalar `trades.length()`. Emptied buckets persist at `{ value: 0 }` (the old copy said "pruned" — wrong).
- `top(n)` ranks the ROW VALUE itself (numeric rows, ops/ordered.ts), so `az('px').top(3)` would not give the three lowest prices; the honest demo is `trades.map(t => t.qty * t.px).top(3)`. `limit(n)` is a window over arrival order, so it runs on `trades` directly; `reverse()` is reversed arrival order (newest first), not a flipped sort.

## The peers strip — MEASURED in this tab (sections/operators/bench.js)
- Nothing prints until it has been timed here: every cell is an un-attested, digit-free `—` (or `n/a` / `failed` / `loading`), the header carries only the cost word, the chip superscripts are empty, and the mono line carries NO figure (`not yet measured · measure ▸ builds a separate source on a second runtime and replays a burst of single-row writes through it, here in this tab`) — the bench's K and N are constants in bench.js, not build facts, so they are not typed onto the page before the run.
- **measure ▸** benches the selected operator: a SEPARATE 20,000-row source on a SECOND `Runtime` (`api.handleFor(new api.InMemoryBacking(rt, rows).source)`, `promote()`d — the feed is untouched and its seq does not move), the operator's real view attached (a sink counts its deltas; scalars read `[value]`), then K = 200 single-row writes through `src.get(k).set(field, v)`; the data row prints its per-change figure (`9.5 µs`, **measured**) and the header reads `O(Δ) · 9.5 µs per change`.
- **load peers ▸** imports mobx / solid-js / @preact/signals-core / @vue/reactivity / crossfilter2 / svelte/store / rxjs / react from esm.sh (import-map names; only on this click, never on first paint), then re-measures the selected operator with the eight peers: each holds the same 20,000 rows and a version signal + computed / memo / derived / `map()` / `useMemo` + `flushSync` wrapping the idiomatic plain-JS recompute of the SAME operator, re-run per change (the old race's `prims` idea); crossfilter uses its dimension/group where the operator maps (filter · between · length · lengthBuckets · group · sum · avg; row replacement = `idDim.filterExact(k); cf.remove(); cf.add([nr])`) and the plain recompute elsewhere (flagged in the cell's title). Multiples = peer / data, bars ∝ measured ms, header peak = max multiple, chip superscript = that peak — all `data-attested="measured"`. After the first measure, selecting a chip auto-benches it (one bench at a time; a chip picked mid-run is queued). Results are kept per operator for the page's life; switching to an unmeasured chip returns the strip to dashes.
- **The clock, honestly.** `performance.now()` steps at 0.1 ms in this non-isolated page (the mono line prints the step it measured), so a ~5 µs write cannot be timed on its own. A ROUND replays the 200 changes (chunked, yielding to the frame loop every ~40 ms of timed work; every round's writes are fresh values so none is an Object.is no-op) and the per-change figure is the round's timed total / 200; rounds repeat within a budget (3–7 rounds, fewer for a peer slower than ~1.5 s/round) and the printed number is the MEDIAN round (the cell's title also shows the best round and the round count). The mono line: `measured on this machine · 20,000 rows (runtime: src.rowCount()) · 200 changes per round (measured: the writes data's rounds actually applied, COUNTED in timeRounds and divided by the round count — not the constant) · median round · clock step 0.1 ms (measured; printed at 1 / 2 / 3 decimals so a finer clock in an isolated context would not print as 0.0)`. Multiples are rounded before formatting, so `9.96` and `10.04` both print `10×` (never `10.0×` beside `10×`).
- Two sample runs on this machine (WSL2, headless Chromium) — they differ, which is the point of measuring rather than printing: run 1 `sum` → data 9.5 µs; MobX 24× · Solid 18× · Preact 18× · Vue 15× · crossfilter 535× · Svelte 25× · RxJS 21× · React 31×; `median` → data 36 µs, peers 266–590×; `keys` → data 5.0 µs, peers 58–71×. Run 2 (the audit and the fps probe running alongside) `sum` → data 19 µs, peers 5.0–163×; `median` → data 14 µs, peers 820–1731×; `keys` → data 13 µs, peers 49–76×. None of these digits are on the page unless that tab measured them.
- "measure all" was left out on purpose (keep it cheap); `n/a` is wired for any operator whose peer recompute is not meaningful — with the current 33 every peer has a meaningful recompute (tap's is an O(1) effect, limit's an O(1) slice — they can and do come out near or below 1×; that is what measuring means).
