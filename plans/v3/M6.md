# M6 — "Delete the Maps, adopt the containers"

**Status: PLANNED (design locked 2026-07-27). Implementation starts at Phase 1.**

Design provenance: a three-lens panel (memory-first / setup-latency-first /
throughput-ceiling-first) + an adversarial judge, run against the SHIPPED
keyed-delta kernel — not the pre-M0 [columnar-ir concept](concepts/columnar-ir.md),
most of which (ExprNode IR, codegen, WASM, Arrow) predates the kernel and is
explicitly out of scope here. The panel's central verified finding: **the
measured RSS delta (crossfilter example 237.8 MB vs v2's 166.5 MB) is Map
bookkeeping, not row data** — 4× between full-parent mirrors, 9× materialized
view Maps holding parent-identical refs, ordered's rows cache, bucket members,
source identity bookkeeping. So the roadmap deletes/thins Maps behind the
proven `hasRow`/`rowAt`/`each` parent-query protocol (the same move that took
the set-ops rewrite from 337→218 MB), adopts input containers in place for
setup, and gates true columnar storage behind a "still needed?" check.

Frozen throughout: the keyed-delta contract, the public API, the conformance
kit (every phase ships conform+oracle+differential green), the v2-record
compat profile. M6 is backing, not surface.

## Judge scores

PLAN A (memory-first): 8.0/10 — The best-verified plan: every line number in its first slice checks out against v3/ops/between.ts (rows mirror at 72, seed 102-107, writes 243/252/262, widen reads 344/357, resort 374), its RSS inventory matches the code (setops.view retained post-09adf4a, ordered.rows at ordered.ts:153, bucket.members at bucket.ts:112), and P1-P3 carry zero contract risk (all behind the proven hasRow/rowAt/each protocol). Honest gating of columnar to a likely-skipped P5. Deductions: P4's exit criteria are factually wrong — the corpus setup rows it claims (tap 12.5x, to 9.9x) are OBJECT-born sources (verified in perf/workloads.ts), so array identity lanes cannot move them; and its corpus row citations (between/remove 2.81x, group/churn 2.78x) are one sweep stale (pass 2 landed 2.42x/2.00x).
PLAN B (setup-first): 8.5/10 — The only plan whose mechanism actually addresses the measured corpus setup class: `to`/`tap` sources are objects, so object-adopt (P1) is the correct lever, and its order-identity claim holds by construction (today's Map insertion order IS Object.keys order). It correctly answers STATUS gap 8's recorded lazy-key-index objection (promotion at first STRUCTURAL write; reads never need the index), names the promote-spike risk with an explicit gate + fallback, and its P4 collects the RSS win via the proven delegation pattern. Deductions: P3 (delta-maintained typed column index caches) fails the measured-gap test — crossfilter setup is ALREADY 0.62x of v2 and corpus between/setup is 0.50x, so its consumer is a non-gap and the argsort delta-maintenance is underspecified machinery; and its RSS phase is one thin line where Plan A has three code-verified phases plus the ordered prev-overlay design.
PLAN C (ceiling-first): 5.5/10 — Intellectually honest about where 63-500x lives (scalar-observing chains only) and evidence-based in cutting WASM/Arrow, and its P1 ident-mode contributes the best materialization detail (cost lands on first REMOVE, not first write). But it scores worst on all three criteria: P1's exit misattributes the object-born corpus rows to array ingestion (same error as Plan A P4); P4/P5 (lazy row/prev thunks, additive CommitBatch.cols, fused lane) are the only proposals in the panel that touch the frozen delta contract's observable semantics (row-reference identity, materialization timing); and the fused scalar lane has NO in-repo consumer — the altbackend workload is an experiment mirror, not a product surface — textbook speculative machinery. Its P3-exit decision gate on the gap-7 interim is good practice worth keeping.

## Decision rationale

SPINE: Plan B scored highest (8.5) because verification showed it is the only plan whose mechanism matches the measured setup gap — the corpus setup cases (tap/to in perf/workloads.ts) are OBJECT-born, so Plan B's object-adopt is the correct lever where Plan A's P4 and Plan C's P1 both misattribute those rows to array ingestion. Its adopt-in-place + one-shot-promote design also correctly answers the objection STATUS gap 8 recorded against lazy key-indexes (cost lands at first STRUCTURAL write, and reads/appends never need the index). The synthesis keeps B's arc — setup phases early, RSS collection, re-baseline last — but makes two evidence-driven edits: B's P3 (typed column caches) is demoted to a gated appendix because its target is a non-gap (crossfilter setup is already 0.62x of v2; corpus between/setup 0.50x) and its delta-maintenance is the plan's one piece of speculative machinery; and B's thin one-line RSS phase (P4) is replaced wholesale by Plan A's three code-verified RSS phases.

FROM PLAN A (8.0): the entire RSS program — Phase 1 (between mirror deletion, promoted to the FIRST slice), Phase 4 (dual-mode membership view), Phase 5 (ordered prev-overlay + counts-bucket thinning) — plus the gated opt-in columnar P5 as appendix G2, and the fan-out argument that kills the gap-7 interim (the bench graph fans flights into 4 betweens + 5 intersects; nothing has a sole parent where it matters; delegation deletes the Map that sharing would keep alive). Plan A's P1 leads the whole roadmap despite B being the spine because it is the panel's single best slice: ~40 lines, one file, zero new machinery, every line number verified against the code, riding the exact protocol 09adf4a already proved at this scale (337->218 MB), and it moves the headline 1.40x metric in the first PR. Plan A's P4 was dropped (wrong exit criteria — object-born rows) in favor of B's P2/P3 pair which covers both source shapes correctly.

FROM PLAN C (5.5): three things survive. (1) The materialize-on-first-REMOVE detail folded into Phase 3 — the cleanest statement of why identity-mode adoption sidesteps the recorded lazy-index rejection. (2) The written decision-gate discipline (its P3 exit gate on the interim), adopted as the post-Phase-5 formal drop of the gap-7 interim. (3) Its evidence-based non-goals — the WASM cut (measured 0.16-1.49x marginal) and the fn-args-stay-opaque rule — strengthening the synthesis's non-goals section. Everything else in C (lazy row/prev thunks, the additive cols field, the fused scalar lane) is excluded from M6 by the panel's own criteria: those are the only proposals that touch the frozen delta contract's observable semantics, and the fused lane's 63-500x ceiling has no in-repo consumer — the definition of speculative machinery before a consumer exists.

ORDERING LOGIC: Phase 1 before Phase 2 (though the spine is setup-first) because A-P1 is strictly lower-risk and higher-certainty than B-P1 (~40 verified lines vs ~115 lines of new store mode), gives the headline metric an immediate move, and shares no code with the adoption work — pure de-risked momentum. Phases 2-3 then close the setup class where the mechanism actually lives; Phases 4-5 finish the RSS program on top of the Phase-1 pattern; Phase 6 locks the numbers into STATUS/MIGRATION per the repo's docs-in-sync convention.
