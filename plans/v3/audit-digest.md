Full audit JSON (if you need more): /tmp/claude-1000/-mnt-c-Users-pemrouz-cloud-data/da6e06eb-857c-4290-8757-09f9b7a7bf3e/tasks/audit-result.json

## Subsystem: core-engine

### Verdict
High rewrite leverage, but narrower than the mapper's weakness list implies: roughly half of that list (dead code, duplication, clone cost, trap gaps, error aggregation, type co-location) is patchable in an afternoon-to-a-week each and must not pad the case. The genuine rewrite case rests on four architectural decisions that provably did not converge under patching: array-positional row identity (C14/C16 are documented as mutually exclusive fixes and P7 is a permanent O(N) fallback), the universal callable-proxy namespace, the fused mutation/sink verb surface with reflection-based capability negotiation, and GC-timing-dependent dedup/lifetime semantics. A v3 built on stable row identity + a single typed Delta IR + separated Source/Sink roles + owned subscriptions deletes the entire C-series bug class and most of the protocol's convention-carried complexity — provided it preserves the engine's real crown jewels: no-phantom-events delta discipline, synchronous FIFO cascades, leak-free-by-default lifetime, the ChangeRecord/connect compatibility surface fero depends on, and the monomorphic flat-array hot paths behind the benchmark wins.

### Structural problems (rewrite-only)
- **Array-positional row identity baked into the base protocol (the C1-C16 duality)**
  - why: Row identity IS the array index, so every structural change forces the whole graph to reconcile positions. This is not operator-local: Value itself carries five extra verbs (BR1A core.ts:590, BI0A:757, BMV1:784, plus View-only BH1/BF0 core.ts:1037-1047), View needs the V1 shift-refresh with an intentional off-by-one (core.ts:1106-1111), the `owns = view.value !== p.value` shared-reference guards (core.ts:591, 758, 785), and Value.BU1 must distinguish in-bounds-undefined hole-fill from insert (core.ts:670-689); RowOperator needs four array-only handlers (row.ts:108-184) and source-length mirroring (row.ts:78-84). Decisive evidence that patching did NOT converge: ISSUES.md documents C16 and C14 as MUTUALLY EXCLUSIVE — 'No-opping the secondary echo would fix this — but break the C14 independent-array case' (ISSUES.md:27-33) — i.e. positional identity is fundamentally ambiguous under independent-array set algebra, and no local fix can resolve it. P7 (ISSUES.md:70-77) is a permanent O(N) rebuild for array-source aggregates because 'the position→value map can't be trusted incrementally' and an incremental BH1/BF0 path was tried and was WRONG. Every new operator must re-derive this contract from prose (PROTOCOL.md's 'recipe': cache isArr, splice don't delete, shift surviving keys).
  - redesign: Give every row a stable identity: a keyed store plus a SEPARATE derived order/index structure. 'Remove' never shifts survivors, so splice-vs-hole, BR1A/BI0A/BH1/BF0/BMV1, V1, the owns-guards, RowOperator's array handlers, and the C14/C16 conflict all cease to exist as concepts; P7's aggregates become fully incremental (object-keyed aggregates already are, per ISSUES.md:75). Sorted/positional views become order-index consumers rather than protocol participants. Caveat the redesign must honor: the flat-array hot path is part of why the H7 benchmarks win — the keyed store needs a dense-array fast lane (e.g. int keys + packed storage), not a naive Map-of-rows.
- **One universal string namespace: data keys, operator names, built-ins, and JS protocol probes all resolve through the same get/apply traps**
  - why: The get trap mints a real child View for EVERY string access including method names — proxy.filter(fn) registers a ghost 'filter' child in the parent's views Map (core.ts:1441 → get_or_create_named:1178) which each() then walks during XU0/XR0 until GC (core.ts:908, 961); apply is an ~87-line ordered if-chain (core.ts:1448-1535) where precedence is load-bearing (a registered operator named 'update' would shadow the mutation verb, since Operators dispatch at :1505 precedes update/insert/remove at :1519-1521). The design forces armor everywhere: the thenable guard (:1460-1465), the toJSON guard (:1498-1504), the 'proxy.value creates a child named value' gotcha (:1427-1429), register.ts:94-97's callable-proxy exclusion in reduce dispatch, and operators' own `instanceof ViewProxy` checks (filter/index.ts:37). Reflection lies by omission — no has/ownKeys/getOwnPropertyDescriptor traps, and Symbol.iterator is an infinite generator (:1544-1548) so [...proxy] hangs. Individual symptoms are patchable, but the collision itself (a data key named 'filter' is unreachable as a method-position read; every new built-in shrinks the usable keyspace) is the API's foundational decision — you cannot remove the ambiguity while string access means both things.
  - redesign: Separate the three namespaces: operators/built-ins live on a real prototype (or are resolved from the table WITHOUT minting a child View), child access keeps proxy sugar but goes through a cached wrapper (one ViewProxy per (view,name) instead of 2 allocations per access, core.ts:1393-1396), and reflection traps are implemented honestly (finite iterator from the snapshot, real ownKeys/has). This deletes the thenable/toJSON armor, the ghost-children walk, the typeof-function leaks, and the precedence-ordered apply chain — while the v2 type surface (bare Data<T[K]> children, .update/.remove/[value]) already points at the shape the runtime should have had.
- **Mutation-entry and sink-notification roles fused onto one verb surface, with capability negotiation by reflection**
  - why: Operator IS-A Value (core.ts:827), so the same method names serve as public mutation entries AND sink handlers with DIFFERENT payload shapes: Value.BR1/BR1A as entries read names-only stride-1 (core.ts:590-601, 607-619) while sink-side BR1 receives [name,value] pairs stride-2 (View.BR1 fanout :941; RowOperator.BR1 row.ts:108-123). Safe today purely by convention — every pass-through overrides BR1 (verified: tap/index.ts:81,152, to/index.ts:27, keys/index.ts:71, reverse/index.ts:64) and nothing mechanical enforces it on the next operator. Because inheritance makes method presence ambiguous, fanout must negotiate capabilities by TWO different reflection rules in one function: prototype-identity for BR1A/BI0A but mere presence for BH1/BF0 (core.ts:1142-1168), and BH1/BF0 must live on View-only specifically 'so a plain Value sink never inherits one' (:1034-1036). The payloads are untyped flat arrays read by stride convention (iter2/iter3 :1261-1270) and the entire verb surface is `any`. Renaming/splitting in place would touch all 16 operators, render, devtools, and fero's change-record mirroring simultaneously — it IS the rewrite.
  - redesign: One canonical typed Delta IR produced once per mutation and consumed by operators, sinks, render, and devtools; Source (write API) and Sink (on-delta) become distinct interfaces, and 'what does this sink receive' becomes a declared, type-checked capability instead of prototype forensics. This also collapses the three parallel change representations (names-only entries, interleaved fanout pairs, cloned ChangeRecords) and lets clone-on-read replace eager structuredClone. Ship a compat shim re-emitting today's ChangeRecord shape `{type,key,value,at?}` — fero-v2 and every test depend on it (HARD invariant).
- **GC-nondeterministic observable semantics: lifetime, dedup, and some operator RESULTS depend on collection timing**
  - why: Sinks are WeakRef-only (core.ts:1201) with the lifetimes WeakMap pinning connect() sinks to their anchor (:1286-1288, 1327, 1342-1344, 1369-1371); operator dedup works by scanning currently-LIVE sinks for a matches() hit (createOperator :207-213, duplicated in apply :1510-1514). PROTOCOL.md states it plainly: 'if all downstream proxies are dropped, the operator gets GC'd and a fresh one is built next time' — so for history-dependent operators (object-source limit, distinct — documented iteration-order-loose in CLAUDE.md) an identical call can return DIFFERENT results depending on whether a GC ran between calls, and a sink whose anchor is dropped dies silently at an unpredictable time. There is no dispose anywhere; every test's local-variable discipline and the examples' defensive anchor-keeping encode the footgun. A .dispose() handle is an additive patch, but making dedup/caching deterministic requires an ownership model, and the weak-everything lifecycle is baked into View.sinks iteration-as-sweeping (:1117-1140), the devtools root registry (:173-183), and every consumer's mental model.
  - redesign: Explicit subscription/ownership: connect and operator chaining return handles with deterministic dispose; refcounted (or scope-owned) operator caching makes dedup a semantic guarantee instead of a GC coincidence; WeakRef remains only as the leak-safety net. The valuable property to PRESERVE is the current design's headline: dropping a subtree leaks nothing without any manual teardown — a rewrite must keep leak-free-by-default while adding determinism on top.

### Must KEEP (looks odd but is right)
- No-phantom-events discipline: Value.BU1 splits upsert into update/insert and drops identical values (core.ts:670-689), BI0 reclassifies existing-key inserts as updates (:725-748), BU2 filters no-op deep writes (:697-720). Load-bearing for every incremental aggregate and for fero's change consumers (DECISIONS C8) — a rewrite's Delta IR must reproduce this filtering at the source, not push re-verification onto sinks.
- transact's FIFO re-entrancy discipline (core.ts:48-97): outermost mutation completes, re-entrant sink writes drain in submission order, per-sink exception isolation so one throwing sink can't rob later sinks of an event. The comment block explains real failure modes (desynced running totals, half-applied graphs) — keep the semantics exactly, whatever the mechanism.
- Sink-set snapshot before fanout ([...this.sinks], core.ts:1126-1140, 1156): a sink subscribing mid-cascade gets the post-commit snapshot and must NOT also receive the in-flight delta — prevents double-delivery to fold consumers. Looks like a defensive copy; it's a correctness rule.
- The V8 monomorphism engineering: View's constructor initializes ALL fields including child-only ones so root and child views share one hidden class (core.ts:854-868), `declare` fields keep TS annotations runtime-erased (:527-528, 843-853), and fanout call sites pass constant verb strings for IC specialization (:1151-1152). A naive 'clean' rewrite with field initializers or dynamic verb strings would regress the benchmarks the library is sold on.
- Symbol.for global registries for value/view/reactive/$/Operators/devtools-roots (core.ts:31-33, 115-116, 160, 173-176): they solve a REAL problem — tsup builds each entry as a self-contained bundle (splitting:false), so per-bundle Symbol() made proxies from one entry unrecognizable to another (the documented C6 fix). A v3 may retire them, but only by ALSO changing the packaging (shared chunks); don't swap to Symbol() in isolation.
- WeakRef-downstream/strong-upstream lifecycle as the DEFAULT: keeping the tail proxy keeps the chain alive, dropped subtrees collect with zero teardown code, and the lifetimes WeakMap makes connect(obj,'prop') live exactly as long as its target (core.ts:1322-1327). The structural item asks for deterministic dispose ON TOP of this — the leak-free-by-default property itself is a differentiator to preserve.
- BH1/BF0 graceful degradation (core.ts:1019-1047): sinks lacking the hole verbs fall back to BR1/BI0, which is exactly correct for position-agnostic consumers — this is why aggregates needed no changes during the positional fixes. In a v3 the verbs vanish (structural #1), but the fallback-lattice DESIGN principle is worth carrying.
- sclone's exact shape (core.ts:43-46): `d == null` (not === undefined) so null data passes through without throwing mid-cascade, and the d[view] short-circuit because live proxies would throw on structuredClone. Both branches are correctness, not style.
- ArrSink/FunctionSink skipping undefined-valued BR1 removes (core.ts:1300-1306, 1380): a RowOperator's [index, undefined] pair is a positional shift signal, not a logical row removal — record sinks must not surface phantom removes. Looks like a data-loss filter; it's contract fidelity.
- The `owns = view.value !== p.value` guards (core.ts:591, 758, 785): under the shared-reference pass-through optimization (tap points view.value at p.value) the upstream has already spliced — re-splicing double-shifts. Necessary while shared-reference pass-through exists; delete only together with the whole positional protocol.
- LinkedView's asymmetric throws — plain a[value]=proxy throws 'use a linked value instead' (core.ts:539) and linked[value]=plainValue throws non-reactive (:1231-1232), with the cycle check BEFORE any mutation (:1234-1242) so a failed link is a clean no-op. The $(view)-swap idiom every example uses depends on these exact semantics; the previous mutate-then-throw version permanently poisoned both proxies.
- The optional unused `src` parameter on Value verb signatures (core.ts:568-573): it's how multi-source operators (intersect/union/except) know WHICH source echoed — looks like base-class clutter, is actually the multi-source identity channel.
- register.ts as a separate side-effect-only module: tsup's export-star dedup elided inline registrations from dist/full.js (register.ts:5-13) — don't fold it back into index.ts without changing bundling.
- V1's `length+1` loop bound (core.ts:1106-1111): intentionally visits one slot past the end so a child view held at the now-empty tail gets cleared — an off-by-one that is correct.
- The per-verb error-message DX (empty-table lean diagnosis listing registered operators core.ts:1526-1534, connect(fn) fail-fast :1586-1590, thenable/toJSON guards :1451-1465, :1498-1504): given the current callable-proxy design these are necessary and high quality; they become deletable only when structural #2 removes their cause.

## Subsystem: protocol

### Verdict
High rewrite leverage — the mapper's core thesis survives adversarial checking. Three protocol properties are genuinely architectural: position-as-identity with two coexisting array contracts (verified: 506 token-anchored lines of dual-contract reconciliation, per-operator conformance unenforced, and the C14/C16 secondary-echo paradox is formally unresolvable in the positional model), new-value-only deltas (ISSUES.md itself classifies the fix as a protocol change touching every implementer), and ordered multi-part emission whose sequencing is comment-enforced. Ruthless caveat: the fixes DID converge — KNOWN_FAILURES is empty, an 18,600-run stress is clean, and residuals are low-severity with documented workarounds — so the rewrite is justified by the ~20% permanent reconciliation tax, the foreclosed incrementality (P3/P7 both blocked on protocol changes), the two baked-in paradox residuals, and the three-times-outrun proof gate, NOT by ongoing correctness fires; and a keyed model kills ~75% of the C-series (C5/C7/C8/B1-class bugs need the oldValue field and faithful-emission discipline, which must be carried over deliberately).

### Structural problems (rewrite-only)
- **Row identity = storage position for arrays, yielding two coexisting array contracts (splice-shift vs positional-hole)**
  - why: Verified root cause of ~12 of the 16 C-issues. Arrays give rows no identity except index, so every keyed-state operator hand-implements BOTH shift bookkeeping (splice contract) and hole mirroring (sparse contract): row.ts has parallel BR1/BH1 and BI0A/BF0 handlers (row.ts:108-184); intersect/union/except each carry BR1A/BI0A + BH1/BF0 + hole-flagged _leave/_enter (operators/intersect/index.ts:115-361); sort has 129 positional-token lines. The BH1/BF0 verbs were bolted on retroactively because 'two contracts coexist on the array path with no signal to tell them apart' (.claude/array-contract-design.md:56-59), and the holes are LOAD-BEARING for intersect's by-index cross-source correlation (design doc:61-73), so densifying producers in place was correctly rejected — meaning the dual contract cannot be removed without re-keying every operator's state, which IS the rewrite. Conformance is unenforced: each operator was individually non-conformant until the differential harness caught it post hoc (C2 missing RowOperator.BI0A, C13 short arrays, C15's 9 KNOWN_FAILURES — DECISIONS.md:43-48, 222-244). The model bottoms out in a genuine paradox shipped as permanent residuals: intersect's secondary-echo _leave (operators/intersect/index.ts:140, BR1A) is simultaneously required for C14 (independent arrays) and wrong for C16 (sparse primary) — ISSUES.md:26-47 documents both sides and explicitly declines to flip it. Quantified: 506 token-anchored lines (verified exact by grep) / est. 1,000+ handler-body lines, ~20% of the engine, exist solely to reconcile positional identity. Object-keyed sources — where identity is the key — were correct throughout the entire saga, which is direct evidence for the keyed model.
  - redesign: Assign every row a stable opaque key at ingestion (arrays get synthetic IDs) and move ordering/position into a separate rank→key channel. All membership deltas become {add|remove|update, key}; hole-vs-splice, insert-misread-as-update, window-rotation splices, and echo-order choreography become unrepresentable (C1/C2/C3/C4/C10-half/C12/C13/C15 impossible by construction); C14/C16 dissolve into well-defined key-based set algebra with no primary/secondary distinction; every operator keeps ONE code path instead of an object path + two array paths; ~1,000+ lines of shift/hole reconciliation, all isArr branches, the BH1/BF0/BR1A/BI0A/BMV1 verb family, and the string/number key-coercion patches (core.ts:930-932, 1008; sort:521) are deleted. The differential harness's own 'logical equality' (densified, keyed — differential.test.ts:27-51) already specifies this as the semantic model.
- **Deltas carry only the NEW value — no oldValue in the protocol**
  - why: Baked into every verb signature on Value/View and every operator's handlers (flat [name, value, ...] payloads, core.ts:1261-1264). Verified consequences: 3-arg reduce rebuilds O(N) on BU2 because 'the row's reference is unchanged, so the cache holds the already-mutated row' — ISSUES.md P3:54-59 names the fix as 'a protocol change that threads the old value through BU2 (which... touches every BU2 implementer)', i.e. the maintainers themselves classify it as protocol-wide; reduce's per-key reference cache with its ''+k string-normalization footgun exists only to reconstruct old values (DECISIONS.md:83); distinct's representative desync (C7, DECISIONS.md:94-99) and reduce's silent accumulator drift needing an opt-in O(N) $.debug re-fold (C5, DECISIONS.md:73-79) are the same missing field. Cannot be added in place without changing the signature of every verb on every Value/View/operator/sink simultaneously.
  - redesign: Records carry {key, oldValue, newValue}. Every invertible fold becomes O(Δ) on all paths including nested in-place edits (closes P3 outright), incremental folds become mechanically verifiable instead of debug-mode-audited, distinct/reduce lose their reconstruction caches, and the shipped ChangeRecord surface gains at most one additive field — fero and examples keep working.
- **Multi-part ordered emission with observable intermediate state; correctness rests on comment-documented sequencing conventions**
  - why: One logical mutation fans out as multiple verb batches while view.value is already fully written, so ORDER between batches is load-bearing and unenforced: between must emit removes before fills or a downstream sort bisects col(undefined) and mis-ranks (C9, DECISIONS.md:133-143, fix = 'swap the two trailing if blocks'); limit's BR1-batch refill collided with the subsequent BF0 batch and double-added (C11, DECISIONS.md:157-166); union's _enter must emit re-rank BU1s BEFORE its insert or a downstream sort's bisect sees non-monotonic order (DECISIONS.md:242, ISSUES.md:29). Multi-source operators additionally depend on echo cardinality and arrival order of derived facets — primary echoes LAST for intersect/except but FIRST for union (union/index.ts:102-108), with bits folded 'order-independently... we never read other sources mid-cascade' (intersect comments). Core has its own cross-file sequencing invariant: View.BH1/BF0 fire the child XU0 BEFORE the sink handler and DOMSink correctness depends on it (core.ts:1030-1036, DECISIONS C4). Nothing types or enforces any of this; each violation was found months later by stress probes. Making emission atomic changes the sink interface everywhere — not an in-place patch.
  - redesign: Two-phase commit: apply the whole logical mutation to settled state, then deliver each sink ONE immutable, deduplicated batch. Intra-batch ordering bugs (C9/C11/union-re-rank) and mid-cascade reads of unshifted siblings become unrepresentable; multi-source operators correlate by key against settled snapshots instead of echo choreography; this extends the direction transact()/patch() already point (core.ts:59-96, 395).
- **Open verb set with silent-drop dispatch and two inconsistent capability tests**
  - why: A sink implements only the verbs it cares about, and the dispatcher cannot distinguish 'position-agnostic sink, fallback correct' (aggregates — deliberate, operators/aggregate/index.ts:164-169) from 'positional sink, missing handler is a bug': LimitValue simply lacked BR1A/BI0A/BMV1 and re-ordering events 'were silently dropped' (C10, DECISIONS.md:146-155). This is entangled with the class-prototype dispatch architecture and the dual array contract; a closed set can't be retrofitted while 13 verbs × inheritance-based defaults remain the interface.
  - redesign: A small closed delta algebra (add/remove/update + order-channel move) expressed as a TS discriminated union with exhaustive-switch sinks: 'sink ignores a verb' becomes a compile error; the prototype-vs-presence fork disappears; graceful degradation (the genuinely good idea in today's fallbacks) is re-expressed as explicit capability flags, e.g. order-aware vs membership-only sinks.

## Subsystem: operators

### Verdict
High but concentrated rewrite leverage: five architectural decisions — positional array identity, protocol-by-convention with no normalization boundary, Operator-extends-Value defaults, undefined/sparse overloading in the public value shape, and the unsettled per-pair cascade — generate essentially the whole C1–C16 bug ledger, the two still-open correctness holes (C14/C16), and the 70-90% bookkeeping share of per-operator code, and none of the five is fixable without rewriting every conformer simultaneously. However, roughly half of the mapper's weakness list (sort's O(N) rank lookup, the five reactive-arg mechanisms, dedup gaps, reduce arity, the rebuild-family duplication, all cruft) is patchable in place and must not be counted as rewrite justification. Equally important, the subsystem contains a large amount of hard-won algorithmic IP — between's brush walk, the content-stable window reconcile, the bitmask membership design, the measured-and-rejected SharedMembership experiment — that a v3 should port under the new protocol, not rediscover.

### Structural problems (rewrite-only)
- **Positional array indices used as row identity**
  - why: Every operator and sink encodes index-shift semantics because an array element's identity IS its position. This spawns the entire second verb vocabulary (BR1A/BI0A/BH1/BF0/BMV1), hand-written splice-lockstep blocks copy-pasted across intersect/union/except (intersect/index.ts:139-158, union/index.ts:109-128, except/index.ts:91-113 — same comment verbatim), pendingShift heuristics (`p.value.length > this.filters.length`, intersect:187, union:160), sort's O(sorted×removed) key-renumbering loop (sort/index.ts:179-187) and its string-keyed `sorted` with `''+k`/`+k` coercions on every hot path, and the O(N)-rebuild fallbacks in aggregate (aggregate/index.ts:135,151), 3-arg reduce (reduce/index.ts:216,230), length(fn), and distinct whenever an array splices — because their position-keyed caches can't survive a shift. The C1–C16 issue lineage is overwhelmingly this one root cause, and two holes remain OPEN because they are unreachable within this identity model (C14: intersect over independent arrays can't admit a tail insert; C16: sparse-primary intersect drops a survivor — ISSUES.md). Unfixable in place: changing identity changes what every verb means, so every operator, the render DOMSink, and the differential harness would need simultaneous rewriting — which is the rewrite.
  - redesign: Assign stable internal keys to array elements at ingestion; index becomes a derived projection, not identity. This deletes the array-positional verb family and all shift bookkeeping, closes C14/C16 by construction, and — the biggest quiet perf win — makes aggregates/length(fn)/reduce/distinct O(Δ) over array chains (`between(arr).sum()` per brush flip goes from O(N) rebuild to O(changed rows)), removing the need for aggregate's deliberate BH1/BF0 prohibition (aggregate/index.ts:164-170).
- **Protocol-by-convention: untyped packed-pair verbs with no normalization boundary**
  - why: The verb payloads are packed arrays of string-OR-number keys with stride 2 or 3, `undefined` doubling as the 'leave' signal, and an untyped optional `src` second param for multi-source identity documented only in a Value comment (core.ts:568-572). Every protocol rule is re-enforced per operator: key stringification is patched at sort/index.ts:519-524, 256, 273, 299, 340, aggregate/index.ts:111-115, reduce/index.ts:155-159, group's posMap — each discovered as a separate silent-desync bug; 'undefined means leave' is hand-reimplemented in sort BU1 (250-254), group, LengthValue/LengthFnValue, LimitValue BU1 (751-768), reduce BU1 — each originally a bug ('the count went permanently stale'). Verified bookkeeping ratios: ZAValue's actual ordering logic is ~55 of 515 lines; the rest is protocol conformance. There is no single point where a delta is created or consumed that could normalize keys or validate shape — the convention IS distributed across ~20 classes, so it can only converge by exhaustive whack-a-mole (which the differential harness did) and regresses on every new operator.
  - redesign: One canonical typed batch-delta record, normalized at emission: string keys guaranteed, explicit kind (update/insert/remove/hole/fill/move), explicit source id for multi-source ops, settled snapshot attached. Per-operator code reduces to actual operator logic against a kernel that owns classification, key normalization, and fan-out — the ~70-90% bookkeeping share becomes write-once kernel code, and a new operator can't reintroduce the key-coercion bug class. Must keep the external ChangeRecord `{type,key:string[],value,at?}` + move variant stable (fero-v2 hard dependency).
- **Operator extends Value — operators inherit a root mutable-value's verbs as silent defaults**
  - why: Operator is an empty declare-only shell (core.ts:827-835) over Value, the root-value mutation implementation, so every operator carries source entry points it never uses and — worse — unimplemented verbs fall through to Value defaults that RE-DERIVE deltas from the already-mutated snapshot. For alias-holding operators this silently drops real changes: tap needs a 17-line comment forbidding `super.<verb>` delegation ('Value.BR1 sees the row already gone → continue … silently desyncing any downstream operator', tap/index.ts:35-51), and between needs NINE `view.value === this.p.value` fork-guards (between/index.ts:129, 346, 355, 397, 428, 460, 474, 491, 501). The inheritance is load-bearing for pass-through behavior everywhere, so it cannot be removed in place without auditing every operator's reliance on each default.
  - redesign: Separate the sink interface (receive settled deltas) from the emit handle (publish deltas) with no inherited mutation surface and no delta-re-deriving defaults — an unhandled verb either falls back to an explicit forward-the-handed-delta pass-through or is a compile error. The tap trap, the alias fork-guard pattern, and the 'forgot to override, got silently wrong default' class all become unrepresentable.
- **undefined overloading + two incompatible sparse representations, exposed as public value shape**
  - why: `undefined` means simultaneously 'row absent', 'row leaving' (the documented leave idiom), and 'excluded slot' — so null/undefined are lossy as actual row values (aggregate._project drops null, aggregate/index.ts:81-85; sort skips undefined slots; nothing can express a present row whose value is undefined). And two hole encodings coexist: RowOperator `delete`s (true holes, row.ts:45) while between/intersect/union/except write enumerable `undefined` (intersect constructor comment documents the `i in` vs `!== undefined` bug this already caused, intersect/index.ts:101-106). This is structural because the sparse snapshot is the PUBLIC read surface — `proxy[value]`, demos.js dense(), the examples' defensive bindings, and DOMSink's BH1/BF0 handling are all written against exactly these shapes — so changing the representation is a breaking change to every consumer, not an internal refactor.
  - redesign: Never expose holes: derived views are dense, membership changes travel as explicit deltas, and absence uses a dedicated sentinel distinct from undefined-the-value. Kills dense()-by-hand, the defensive-binding gotcha class, the `i in` bug family, and makes null/undefined first-class row values.
- **Per-pair, per-source push cascade with no settlement phase**
  - why: Verbs fire immediately per source and per pair while sibling state is mid-mutation, so operators observe half-applied worlds. Evidence this is a systemic soundness class, not isolated bugs: sort's _batchUpdate exists because the per-pair path bisected against other batch keys' stale ranks ('silent, permanent mis-order', sort/index.ts:219-226, 373-397); the multi-source ops depend on ECHO ORDER — union's primary echoes FIRST, intersect/except's LAST (union/index.ts:101-108, intersect/index.ts:182-186) — with comments repeatedly reasoning about 'settled vs not-yet-shifted sibling reads' (intersect BI0A: 'we never read other sources — mid-cascade they may not have shifted'); and union must use the echo's CARRIED value because a positional re-read of a sibling is misaligned (union/index.ts:136-145). Each fix is a hand-proved argument about interleaving; the interleaving itself is the architecture.
  - redesign: Define every operator verb over a settled batch snapshot: the scheduler applies all source mutations, then delivers one topologically-ordered batch per sink with explicit per-source attribution. Echo-order dependence, pendingShift inference, and the batch-vs-per-pair soundness split (every _batch* fast path currently duplicating its per-pair sibling) disappear — batch-first is the only path.

## Subsystem: render-jsx

### Verdict
Real but narrower rewrite leverage than the mapper's list implies. The sparse/dense bug family — the subsystem's loudest history — has converged onto one test-locked reconcile path and is patch territory, as are the type ceiling, namespace dispatch, text coercion, and the entire cruft basket. The rewrite-only wins are exactly four: keyed row identity (which requires extending the core change protocol, not just the sink — the single highest-leverage item, killing the dual model, the BMV1 no-op, and the data-id workarounds at once), a real ownership/lifecycle model to replace GC/expando/isConnected teardown, an ordered-children AST to replace the overloaded static slot and shape-heuristic dispatch, and a target-agnostic instantiation pass if SSR/hydration is wanted. The per-binding surgical update model, sparse direct binding, and the trace-equivalence testing discipline are the crown jewels v3 must carry forward intact.

### Structural problems (rewrite-only)
- **Positional (index-keyed) row identity — keyed reconciliation is impossible without a protocol change**
  - why: Array rows are bound to POSITIONS, not data keys: create_node appends at tail bound to node.data[tail] (render/index.ts:82-91), remove_node pops the tail (97-104), and core's positional V1 child refresh rewrites surviving slots' CONTENT on every shift. BMV1 is a deliberate no-op whose own comment states 'true element-identity preservation across reorders would require a data-keyed row model, which this index-keyed renderer doesn't have' (render/index.ts:312-323) — and it is CORRECT under this model, because core.ts pre-fires the touched child's XU0 before the sink's verb runs (core.ts ~1019-1047), so physically moving nodes would double-apply. This is not a render-layer bug: the change protocol itself (BR1A/BI0A/BMV1/BH1/BF0) addresses array rows by index, so no amount of DOMSink patching can make an element follow its row. Downstream costs are shipped: focus/selection/CSS-transition state is lost on reorder, kanban/chat must read the live row id off a reactive data-id attribute because the row fn's key is the index (CLAUDE.md), JSX `key` is parsed, typed (intrinsics.ts:357) and discarded (jsx/index.ts:72-75), and the entire dense-tail vs index-keyed-sparse dual model (render/index.ts:82-165, chosen per-event by the _sparse scan at 263-273) plus its six-regression history (H1/H4/H6, list.test.ts:172-305) exists only because positional identity forces two structural bookkeepings to agree.
  - redesign: Carry a stable row key in the change protocol for array-shaped sources (object sources already have one — the name), and make the sink ONE keyed row map: BMV1 becomes a real insertBefore move, element identity survives reorders (focus/transitions/scroll intact), JSX `key` and object keys become the reconciliation key so the data-id workaround dies, the tail-relative/index-keyed split and the O(N) _sparse per-event scans disappear into a single representation, and the H1/H4/H6 regression axis is deleted rather than guarded. This is a core+render co-design item — it cannot be scoped to the render layer alone (fero-v2 mirrors the ChangeRecord shape, so the record extension must be additive).
- **No ownership/lifecycle model — teardown is GC-heuristic, expando-pinned, and detach-inferred**
  - why: render() returns the bare parent with no dispose handle (render/index.ts:39-47). Lifetime is a chain of heuristics baked into every layer: views hold sinks by WeakRef, so strong refs are stashed as DOM expandos (enumerable dom.sinks/dom.sink at 376-379, non-enumerable __ripple_sink at 384, parent.nrefs/arefs at 514-518 pinned by core's lifetimes WeakMap at core.ts ~1327); liveness is inferred from parent.isConnected (167-175), which the pivot example must work around by attaching its container BEFORE render (CLAUDE.md). Components are plain once-invoked functions (jsx/index.ts:100-111) with no owner, so there is nowhere to hang cleanup: Event.create only ever addEventListener (579-583; zero removeEventListener hits in the file), Ref is one-shot (589-591), and there is no context, error boundary, or per-row cleanup. H5 (only the last sibling sink retained — list.test.ts:267-277) is the failure class this design invites. A dispose handle could be bolted on, but DETERMINISTIC teardown (listener removal, per-row cleanup, nested component disposal) requires an ownership tree threaded through Node.create/Node.generate/Prop.create/DOMSink construction — i.e. re-architecting instantiation, not patching it.
  - redesign: An ownership tree created at mount: render() returns a disposer; each row/component owns its Props, sinks, and listeners and disposes them on removal (removeEventListener becomes possible for the first time); sink retention moves off DOM expandos into owner-held strong refs (keeping the '__ripple_sink-equivalent' element→view back-channel for devtools, and preserving the 'holding the DOM keeps the binding alive' zero-ceremony default via the owner being reachable from the mounted subtree); lifecycle hooks, context, and error boundaries get a natural home; the isConnected bail becomes an assertion rather than the teardown mechanism.
- **Template AST child model — one overloaded `static` slot plus dispatch-on-value-shape**
  - why: Node.add dispatches every call argument on its runtime shape (render/index.ts:412-441): string/number/true overwrite the SINGLE node.static slot (last-wins), undefined/false CLEAR it (the conditional-child idiom `{cond && 'x'}` depends on this), a plain object is ALSO stored in static (comment says 'static attribute bag' at 411 but the consumption path at 417-421 iterates it as static-DATA generating one cloned child per key — the comment and semantics disagree), a plain function becomes the row fn, and a VP becomes node.data. Consequences: static text is expanded via generate() and appended AFTER reactive Text props, so `<span># {cur}</span>` renders 'general# ' — encoded as intended in jsx.test.ts:116-121 and worked around with .to() folding (chat example); multiple statics drop all but the last; JSX must stack heuristics on top (hasRowFn child-sniffing at jsx/index.ts:115-130, regression #42; on[A-Z]-and-not-VP at 61-67, regression #47). This is not fixable by a local patch: making strings ordered Text children breaks the false-clears-static conditional idiom and the static-iteration path simultaneously, because all three meanings share the one slot, and any new argument kind (an options object, a keyed child) collides with an already-claimed shape.
  - redesign: An ordered children list where static text, reactive text, elements, and conditional slots are distinct explicit child kinds (positional order preserved — the '# {cur}' gotcha class dies), an explicit props/options channel instead of shape-sniffing (so `key`, event options, and future args have somewhere unambiguous to live), and JSX becomes a direct mapping instead of heuristic recovery of authorial intent. Keep the trace-equivalence test technique (jsx.test.ts) to pin builder/JSX parity in the new AST.
- **Create-only rendering — no SSR/renderToString/hydration path exists or can be cleanly retrofitted**
  - why: Every instantiation path assumes it is creating live DOM against a real document: Node.create calls document.createElement and appends immediately (render/index.ts:443-453), Prop.create/Text.create create text nodes and connect PropSinks as a side effect of creation (511-521, 571-574), and DOMSink's constructor immediately XU0-builds all rows (60-66). Repo-wide grep confirms zero renderToString/hydration code. The AST itself is inert and serializable — the raw material exists — but a hydrate mode would need a parallel 'adopt existing node' branch in every create() plus a sink-attach that reconciles instead of builds, i.e. a second instantiation protocol threaded through the same classes the ownership rewrite already has to restructure. (Demand is the least-proven of the structural items — no example or issue asks for SSR — so this is a v3 option enabled by the redesign, not a standalone justification.)
  - redesign: Design instantiation as a target-agnostic two-phase 'materialize(target) + bind' pass over the AST: the DOM target creates, a string target serializes (renderToString for free), and a hydrate target walks existing DOM adopting nodes and attaching Props/sinks without creation. The same seam yields the renderer-agnostic sink boundary (string/canvas backends) and a place to batch DOM writes per frame if scheduling is ever wanted.

## Subsystem: types

### Verdict
High rewrite leverage, but narrower than the mapper claims. The genuinely structural core is threefold: a name-dispatched Proxy runtime that no type system can verify (making the entire DataOps surface an unchecked assertion behind one cast), an untyped positional-array protocol woven through all 16 operators and every sink, and a semver-locked fused/invariant Data<T> vocabulary whose honest replacement (read/write split, kind-split) is by definition a new public API — plus a builder DSL whose stringly design resists typing structurally. However, roughly half the mapper's weaknesses are patchable in place — including reactive value-slot typing (a covariant readonly-[value] marker interface works today, contra the mapper's 'patching cannot achieve this'), the map/group return lies, await/LinkedView/get() mistypes, and the missing exports — so the rewrite case must rest on the three architectural roots, not the bug list. The fixture-gate discipline, Option B, the symbol-registry identity, and the ChangeRecord wire shape are converged, load-bearing designs a v3 must carry forward, with fero's imports ($, value, view, Operators) and record shape as hard compatibility constraints.

### Structural problems (rewrite-only)
- **Spec-by-assertion surface: the types can never verify the runtime because dispatch is a name-keyed dynamic Proxy**
  - why: Every method call routes through ViewProxy.apply (core.ts:1448-1533) which string-matches built-ins then hits the globalThis-shared mutable Operators table (core.ts:115-116, register.ts:40-107). There is no function whose signature tsc could check against DataOps<T> — the whole 200-line hand-written DataOps (core.ts:306-510) is bridged to the runtime by exactly one unchecked cast, `$ = (... ) as Dollar` (core.ts:160), and createOperator deliberately returns `any` (core.ts:197-203). The operator surface is therefore maintained in 4 unverified parallel places (DataOps overloads, register.ts dispatch, each factory's return annotation, the fixtures), with fixtures-as-spec the only enforcement. Colocating per-operator interface merges would reduce drift but nothing can make tsc check a Proxy apply's name dispatch — the unverifiability is architectural.
  - redesign: Define each operator ONCE as a typed registry entry (generic call signature + impl class); derive both the runtime dispatch table and the method surface type from it (real prototype methods or a typed pipe, not name-dispatched Proxy apply). Drift becomes a compile error, the `as Dollar` single-point-of-trust disappears, and the consumer fixtures shrink to genuine acceptance tests instead of being the spec.
- **The notification protocol is untyped and woven through every operator — typing it IS the rewrite**
  - why: Verb payloads are positional flat any-arrays ([name, value, name, value] — Value.BR1A core.ts:590-601; RowOperator.loop's NU1/NI0/NR1 in row.ts:27-60), `Sink` is an empty marker class (core.ts:1208), and all 16 operators + View/Value fan-out + DOMSink + FunctionSink implement handlers against this implicit contract with `any` params (~276 `any` tokens in core.ts alone). Retrofitting a typed delta protocol means changing every handler signature in core.ts, row.ts, render/index.ts and 16 operator modules simultaneously — and the known protocol gap (no old-value on BU2, which blocks reduce's incremental path and forced the per-key reference cache, per CLAUDE.md's reduce notes) is a protocol-design issue, not a local bug. Custom operator/sink authors get zero type help today (devtools/augment.ts:12-26 is all `(proxy: any): any`).
  - redesign: Design typed per-verb delta types (discriminated unions, or typed tuple/opaque encodings that KEEP the flat-array allocation-free hot path), thread old-values through updates by design, and make Sink a real typed interface. Operator and sink authoring becomes typed, fero can consume typed records end-to-end, and the BU2-old-value class of workarounds is closed at the design level.
- **One fused, invariant Data<T> vocabulary (read+write, all three kinds) — semver-locked, so every honest fix is definitionally a new surface**
  - why: T sits in update/raf param positions (core.ts:337-342), making Data<T> invariant — the documented root cause (core.ts:257-270) of AnyData, FilterShape's untyped reactive arm, and Data<any> collapsing to the array branch (unusable named access, core.ts:259-260, 301-304). One DataOps serves arrays/objects/scalars, so scalars carry .az()/.filter() members, map's return lies over arrays (Data<Record<string,R>> at core.ts:409 vs RowOperator mirroring the array, row.ts:31), group types a bucket as ONE row (core.ts:509 vs collection at operators/group/index.ts:47,61 — pivot's bucket.sum('col') compiles only via ColOf's non-object fallback), and Option B's types-reject/runtime-accepts rift (core.ts:1398-1412, DECISIONS.md:18 — asymmetric get/set proven inexpressible) is the converged local optimum GIVEN an assignment-first Proxy API. Individual signatures are patchable (see patchable list), but the vocabulary itself — Data/DataOps/ChangeRecord/Reactive/RowOf/Dollar — is exported and pinned at v2.0.0 (lean.ts:15, check.ts:80-91); replacing the shape every signature references is by definition the rewrite.
  - redesign: Split covariant readable View<out T> (connect/[value]/operators) from writable Source<T> (update/insert/remove/patch), and give arrays/records/scalars distinct op sets with honest returns (map preserves array-ness, group returns typed bucket collections whose aggregates key-check, scalars lose collection ops). Pick ONE write idiom (methods-primary) so the runtime-accepts/types-disown rift never exists. Reactive args become honestly typed View<number> instead of AnyData.
- **The builder DSL is stringly by design and cannot be property-typed**
  - why: HTML/SVG are Proxy({}) with a get trap minting a NodeProxy per arbitrary property (render/index.ts:680-689); the DSL encodes classes as chained properties (HTML.div.foo.bar), ids as '#id' strings, and attrs as 'k=v' strings, so Builder is necessarily { [tag: string]: NodeBuilder } with (...children: any[]) and [prop: string]: NodeBuilder (render/index.ts:673-678) — a typed tag map conflicts with the same-namespace class-chaining, and per-prop typing is impossible when props are string literals. render itself is (p: any, np: any) (render/index.ts:39). JSX got per-tag narrowing (jsx/intrinsics.ts) precisely because its shape is typeable; the builder — the library's primary authoring surface — structurally is not. Only the (data, rowFn) overload is typed (render/index.ts:673-674).
  - redesign: Redesign the builder API so its shape is typeable: key tags off the same intrinsics map both JSX transforms already share, take props as a typed object argument (not 'k=v' strings / property chains), and type render(el, template). One intrinsics source of truth then covers BOTH authoring surfaces, and the [k: string]: any floor (jsx/intrinsics.ts:88) plus the any-callable AnyVP (jsx/intrinsics.ts:21-22) can be tightened to View<T>-typed reactive props once the read/write split lands.

### Must KEEP (looks odd but is right)
- The negative-fixture gate discipline (types/check.negative.ts:1-7): @ts-expect-error lines that start compiling fail as TS2578, so silent widening to `any` breaks CI. This is the single most valuable piece of type infrastructure here — any v3 must carry it over (ideally colocated per operator).
- Option B itself (DECISIONS.md TD1): bare Data<T[K]> children with .update()/[value]/.remove()/.get() as the typed write surface. ## Subsystem: perf

### Verdict
The perf HARNESS itself offers little rewrite leverage — its weaknesses (advisory-only regression detection, single-tick H7 headline, regex-parsed markdown pipeline, missing churn/memory scenarios) are all patchable tooling work, and its core ideas (Mode A honesty, H1 op-counts, two calibrated presets, self-flagging candor) should be carried into v3 largely intact. The subsystem's real rewrite value is evidentiary: it quantifies, twice and consistently, that the ceiling is the engine's row-object storage + per-event allocation + hole-protocol + per-write-settle architecture (63-500x left on the table vs a plain-JS columnar backend), which no in-place patch reaches. A v3 built columnar/batch-first/owned-lifetimes/IR-first converts those five structural taxes into wins — but must explicitly re-baseline or version-break the synchronous read-after-write contract and the ChangeRecord shape that every committed benchmark, example, and fero-v2 depend on.

### Structural problems (rewrite-only)
- **Row-object storage + change-record machinery is a quantified 63-500x ceiling no patch reaches**
  - why: experiments/wasm/results-altbackend.md:14-30 shows a pure-JS columnar backend (Float64Array columns + Uint32Array mask) beating the library's own BEST path (gte, a RowOperator) 63.49x per tick at N=10k, 219.75x at N=100k, 84-500x on batch, 48-74x on threshold-change, with the ratio column explicitly labelled 'residual lib overhead ... row-object storage, change-record machinery' (results-altbackend.md:34). This is not one slow operator: every operator's view.value is a JS object/array of row objects, every verb walks them, and every peer multiplier in operators/BENCHMARK.md is measured against peers sharing the same row-object handicap. The landed aggregate Float64Array fast path (operators/aggregate) proved the pattern works but could only be bolted onto one operator's interior — the storage layout is the architecture. Verified against the actual tables; the mapper's numbers are accurate.
  - redesign: Make columns the native store: typed-array columns + a validity bitmask + dictionary encoding for strings, with row-shaped ViewProxy access as a materialization layer on top (the hybrid the aggregate fast path already sketches). Captures roughly all of the measured 63-500x (WASM adds only 0.5-2x more per results-altbackend wasm/js-cl column, so it stays an optional SIMD kernel slot behind a maintained-columns threshold, not a foundation). Setup also flips from a loss to a win (js-columnar setup 10-28x faster, results-altbackend.md:18,27), converting the deleted-ticker insert-rate crossover into a scenario data wins.
- **The sparse-array positional verb protocol (explicit-undefined holes + BH1/BF0/BR1A/BI0A/BMV1) is a permanent per-operator complexity tax**
  - why: The hole-vs-splice vocabulary exists solely to keep parallel object/array layouts index-aligned across operators. Every positional operator must implement five-plus verb handlers (row.ts BR1A/BI0A/BH1/BF0, operators/between, intersect, union, except, sort, group, render DOMSink), consumers must densify before iterating (the dense() helper in assets/demos.js, defensive bindings in library/chat examples), and the C1-C16 bug family all traces to it. IMPORTANT nuance the rewrite plan must be honest about: the fixes DID converge — C15 closed with 18,600 stress runs, KNOWN_FAILURES is empty, only C14/C16 residuals remain (documented, workaround-able) — so this is NOT a correctness argument anymore; it is a complexity-and-perf-tax argument: every future operator pays the full protocol, and the tax is structural because the protocol IS the inter-operator contract.
  - redesign: A columnar validity bitmap represents hole/fill/membership in 1 bit per row with zero verb fan-out: membership flips become bit writes, positional alignment is free (columns never shift), and the entire BH1/BF0/BR1A/BI0A hole-vs-splice distinction plus the densify gotcha disappear. New operators implement one delta shape instead of five positional handlers. The extended verb-tagged wire profile proto/dir/README.md identifies (hole-vs-splice + move-with-value) becomes an explicit serialization concern instead of an in-memory protocol.
- **GC-driven subscription lifetime (WeakRef-held sinks) contaminates both the API and the measurement system**
  - why: Sinks are WeakRef-held (core.ts:1081-1157 snapshot-and-deref on every emit; documented 'dropping the only strong reference unsubscribes silently'). Downstream effects verified: every multi-source workload in perf/workloads.ts must thread keep bundles ({aS, ab, aV} at workloads.ts:46,55,299-301) or it silently measures a collected graph — workloads.ts documents the failure mode instead of preventing it; every fan-out pays a fresh array snapshot + per-sink deref (core.ts:1081,1135,1156); benchMeasure needs forced GC partly because of this. It is structural because the GC-based lifetime IS the public contract — tests, examples, and the perf harness all encode it; switching to explicit disposal in place is a silent behavior change to every existing consumer.
  - redesign: Explicit ownership scopes (dispose/owner, Solid-style roots): subscription lifetime becomes deterministic, the per-emit WeakRef snapshot/deref allocation class is deleted, the keep-bundle footgun and its boilerplate vanish from the perf suite wholesale, and leak detection becomes assertable (an owned scope can enumerate its subscriptions) instead of invisible.
- **Closure-only operator arguments block dedup, incrementality analysis, and serialization by construction**
  - why: filter/map/length/group/to/tap deliberately do NOT dedup because closures have no value identity — even the same closure reference makes two views (CLAUDE.md dedup gotcha; kanban measured ~5x slowdown from piled-up undeduped filter/az operators until rAF-coalescing was added as a workaround). The O(N)-per-delta stragglers are the same root: to/batch 321.6ms, values/batch 135.1ms, reduce(full)/batch 107.1ms in perf/perf.json ops rows — an opaque closure cannot be incrementalized or short-circuited. proto/dir (README.md 'Better' section) demonstrates the alternative is viable: a serializable expression IR rehydrating through the REAL dispatch table with byte-identical change-streams over 20,000 differential fuzz steps, value-keyed dedup, DAG facet-sharing, and remote replay. Caveat for the plan: proto/ is currently UNTRACKED (git status '?? proto/'), so this evidence is not yet committed history; and Layer-1 codegen (compileJS matching a hand closure, RESULTS.md) is a mitigation for the IR's OWN 12x interpreted-tree regression, not a speedup over today's closures — the win is dedup/DAG/wire/columnar-lowering, not predicate speed.
  - redesign: Make the expression IR the primary argument surface with raw closures as the documented Tier-3 escape hatch: value-keyed dedup for the whole operator family (fixing the kanban-class re-point churn without rAF workarounds), static DAG sharing with cycle detection, wire-shippable pipelines, and — decisive in a columnar v3 — predicates that lower onto columns directly (compileJS today, optional SIMD kernel above a row-count threshold per RESULTS.md), which closures can never do.
- **Per-write synchronous settle as the only mutation entry point**
  - why: Mutation enters one proxy-set at a time and the full cascade settles synchronously per write; patch (core.ts) was bolted on because per-row dispatch fan-out was the swarm bottleneck, and it still 'saves dispatch, not allocation' (CLAUDE.md). The runtime's dedup-by-reference/value semantics force every batch workload in perf/workloads.ts to carry toggle/base-alternation boilerplate (workloads.ts:53-54,102,165,197,216) or the measurement collapses to a ~0ms no-op. Structural because the synchronous read-after-write contract is load-bearing everywhere: every peer bench tick is write-then-read ('each tick is its own settle point — no batching primitive', comparisons/bench/workload.ts:12-14), and all committed comparison numbers are defined by it — you cannot flip the scheduler in place without invalidating the entire committed benchmark corpus and every example.
  - redesign: Batch-first mutation protocol: a single write is a batch of one; microtask/rAF coalescing is the scheduler, not an opt-in raf() helper; reads inside a batch see a consistent pre-flush or force-flush snapshot (explicitly version-breaking or preserving read-after-write — decided up front, with every benchmark re-baselined once). Eliminates per-write cascade tax, the patch special case, and the toggle boilerplate class in the perf suite.

## Subsystem: tests

### Verdict
The mapper's report is accurate on essentially every verified citation (63 scenarios, 4 seeds × 24 steps, empty KNOWN_FAILURES with anti-rot check, 210 connect([]) sites, 5 emits users with zero consumers, untracked proto/, CI exclusions) — the only overstatements are minor: $.random appears in 7 files not 8, and the proto fuzz harness's stream parity compares two library-built chains, so it too shares the implementation as oracle. The rewrite leverage here is real but narrower than the weakness list implies: most listed gaps (independent oracle, generated grid, stream capture, render differential, hermetic e2e, fixtures, registry tooling) are plain in-place work on an already data-driven harness. The genuinely structural leverage is that the tests can never be stronger than the library's contract — the 13-verb representation-dependent protocol makes stream legality uncheckable and forced snapshot-only comparison (the C8/P7 blind spots), and underspecified ties/iteration-order force the harness to normalize away rather than pin behavior — plus the one unretrofittable benefit: building the conformance+differential gate BEFORE the operators, so v3's protocol is designed to be small enough to machine-check from commit zero.

### Structural problems (rewrite-only)
- **Change-stream correctness is untestable because the protocol has no canonical observable semantics — the conformance gap is baked into the 13-verb, shape-forked, fallback-laced protocol design**
  - why: Verified: the main differential harness compares only normalized terminal [value] snapshots (differential.test.ts:10-13 says comparison is 'logical', 30-51 densifies holes) and NEVER the change stream. This is not an oversight — it is forced: a legal stream is representation-dependent (splice vs hole depends on source shape; a window rotation may legally emit BU1s or a BR1A/BI0A pair depending on window fullness; BH1/BF0 fall back to BR1/BI0 per-sink), so there is no normal form to assert stream equality against. Consequences verified in three places: (1) C8 — between emitted spurious removes while its OWN value stayed correct, so only a downstream counting sink drifted to -2; invisible until between→length/sum scenarios were hand-added (DECISIONS.md ~line 119, differential.test.ts:190-196). (2) ISSUES.md P7 — a known O(N)→O(1) aggregate win is PERMANENTLY punted because 'an incremental BH1/BF0 was wrong (live 121 vs want 55)' and there is no per-verb kit to verify a correct one ('a protocol change not worth the risk'). (3) Protocol evolution churns hand-written record arrays O(tests) — C3's rotation-emission change rewrote index.test.ts's za stream test (CLAUDE.md C3 note). The spec() `emits` field promises 'feeds the protocol checker' (tests/spec.ts:32) but no checker exists — tests/report/build.mjs:30 only regex-matches the word 'emits' in titles, and exactly 5 tests set the field (verified by grep). A checker for the CURRENT protocol is technically writable in place, but it would have to model every operator's shape state, upstream sparseness, and per-sink fallback capability — its complexity would mirror the protocol's, which is exactly the entanglement that produced C1-C16. Note the mapper slightly overstates proto/dir/fuzz.test.ts as 'the strongest harness in the repo': its stream parity (fuzz.test.ts:126 `same(dch, cch)`) compares two LIBRARY-built chains (closure vs dIR-rehydrated), so an emission bug shared by both construction paths passes — it proves the proto's rehydrate(), not the library's protocol.
  - redesign: Design v3's delta contract FIRST as a small canonical algebra (keyed rows + an explicit order index; one insert/remove/update/move vocabulary with no shape forks, no positional splice-vs-hole duality, no per-sink fallbacks) and build two commit-zero test primitives against it: a replay sink (fold the emitted stream into a fresh value, assert replay ≡ the operator's value after EVERY event) and a legality state machine (no update for a never-inserted key, move within bounds, order index consistent). Wrap every operator in every test with both. Stream-level equality becomes directly assertable (the flow essay's table⟷changes duality as an executable law), the C8 class (value-right/stream-wrong) is caught on the introducing commit, the P7 class (unverifiable incremental path) becomes attemptable, and expected-record churn disappears because the contract is stable by construction. This is the one thing patching cannot retrofit cheaply: the current protocol's legality rules are the entanglement.
- **Underspecified observable semantics force the harness to fence off whole behavior classes instead of pinning them**
  - why: Verified: the harness keeps `v` globally UNIQUE 'so sort order is unambiguous — otherwise live vs rebuild can break ties differently, a representation difference, not a bug' (differential.test.ts:54-59) — i.e. comparator tie behavior is deliberately untestable. Three normalizers exist solely to tolerate unspecified semantics: gKeyset because distinct's output identity is 'legitimately history-dependent' (78-86), multiset because keys/values/reverse over objects are 'iteration-order-loose under leave-then-re-enter' (88-106), and the same looseness makes limit-over-object nondeterministic (CLAUDE.md gotcha: a brushed obj.between().limit(n) can legally pick a DIFFERENT set than a rebuild). Critically, the multiset comment says the append-on-re-enter behavior is 'the intended leave/re-enter classification that sort/filter rely on' — the looseness is load-bearing across operators, so specifying it in place is a breaking behavior change threaded through sort/filter/limit/distinct/keys/values/reverse and every change-stream consumer (fero mirrors ChangeRecord). Tests can never be stronger than the semantics they test; today's differential asserts logical-equality-modulo-three-normalizers, not equality.
  - redesign: v3 specifies total semantics up front: deterministic sort tie-breaking (secondary key comparison), stable re-entry ordering (a re-valued key retains its position, or documented-and-deterministic append), and deterministic first-n over objects. The differential then asserts EXACT equality with zero normalizers, ties and re-entry get direct property tests instead of being fenced off, and two documented gotchas (limit-over-object, distinct history-dependence) cease to exist as user-facing traps.
- **The differential harness was retrofitted AFTER the operators shipped, so its assertive scope is capped by shipped looseness and grows only reactively — a rewrite can invert the ordering**
  - why: Verified: DECISIONS.md line 5 shows the harness was CREATED 2026-06-06 as the proof gate for the already-known C1-C3; differential.test.ts:136-139 admits verbatim 'the harness had NO intersect/union/except head-operator coverage, which is why their array-source remove-churn desync went unseen' (C12); lines 197-207 admit the set-algebra→sort/aggregate compositions were omitted until a 2026-06-13 adversarial probe; lines 305-312 admit the original 4-kind mutation vocabulary 'was exactly the corridor the bugs lived outside of' (C15). ## Subsystem: seam

### Verdict
This subsystem offers the highest rewrite leverage in the repo, but it is sharply bounded: the prototype itself proves most of the horizontal seam (IR entry, descriptors, snapshot fold, compileJS) ships additively on the current engine with zero library modifications, so those items must not be spent as rewrite justification. The genuine rewrite case is four cross-cutting inversions — a SourceBacking kernel boundary below the proxy, a protocol-as-contract record grammar with sink profiles (extended verbs, no-clone, provenance), first-class subscription lifecycle with a versioned timing contract, and IR-native operator argument slots — which map one-to-one onto fero's M0 go/no-go demands and are each cross-cutting enough (every operator, every sink, every mutation path) that in-place retrofit is the expensive path. If v3 makes the seam contract the design center, it wins the flagship consumer and kills the c870bde failure class; if it re-derives today's implicit contracts, fero's stated fallback is a wrapper-or-fork and the seam's entire validated groundwork is wasted.

### Structural problems (rewrite-only)
- **No kernel boundary below the proxy — the source backing is fused into ViewProxy/Resource, so a non-in-memory source requires a reflecting facade**
  - why: Reads/writes resolve through proxy traps hard-wired to the in-memory root Resource; there is no seam to plug a distributed/async/columnar backing underneath. Evidence: fero had to build an entire classifying facade (fero-v2/resource/dispatch.ts:359-470 — BUILTIN/DECOMPOSABLE/HOLISTIC name sets + hasOwnProperty(Operators) in a load-bearing branch-order ladder) plus remote handles (handle.ts:35-55) just to intercept property access, and reaches into private internals `(data)[VIEWSYM].res` → `res.update/insert/remove` at ~5 sites (log/index.ts:29-42, dispatch.ts:282-283, fold.ts) because no public ingress exists. PLAN.md:105-109 itself concedes the SourceBacking retrofit 'changes how data resolves reads/writes (a core surface, wider blast radius)' — i.e. it is not additive in the current architecture.
  - redesign: Design `SourceBacking {snapshot(), read(key), write(record), subscribe(sink)}` (PLAN.md:84-98) as the kernel boundary from day one, with in-memory as the default implementation. fero's whole hand-rolled facade collapses into one backing; the operator pipeline sits above the seam unchanged; and a maintained-columnar backing becomes the sanctioned attachment point for the WASM batch-recompute frontier (RESULTS.md findings 2-3: scalar WASM ~2×, SIMD ~4× the inlined hand loop at 5M rows — but only with hot columns, which only a backing can maintain).
- **The change protocol is an internal method vocabulary with a lossy, mandatory-clone public projection — no protocol-as-contract**
  - why: Internally the graph speaks ~14 verb methods (XU0/BU1/BH1/BF0/BMV1/…); publicly it flattens to a 4-type ChangeRecord (core.ts:272 — no `move` in the type, `value` required) with structuredClone forced at every ArrSink/FunctionSink emission (core.ts:43-46 sclone, :1291-1314). Consequences all verified: fero measures the un-opt-out-able clone at ~30-40% of its entire write budget (plan-v3.md §10, :458-460 — the wire codec re-serializes immediately so the clone buys nothing); BH1/BF0 hole-vs-splice and move-with-value are unreconstructible remotely (proto/dir/README.md:88-97 — the 'two wire profiles' gap); and THREE hand-synced record definitions coexist (core.ts:272, fero message.ts:106-115 adding move+provenance, proto/dir/dir.ts:164-197 folding move) with fero's live applier silently ignoring `move` (DECISIONS E:159-161). The verb-method design is a deliberate zero-allocation perf choice (the bare-tap path exists to avoid record allocation), so 'just emit richer records everywhere' conflicts with the hot-path architecture — the tension is baked in.
  - redesign: Author the versioned record grammar FIRST (SCHEMA_VERSION; update|insert|remove|move; optional value; a provenance extension point `& {origin?,seq?,epoch?}`) and derive the internal dispatch from it, with sink profiles as first-class modes: default 4-type, extended verb-tagged (hole/fill, move-with-value), non-cloning, and bare/zero-allocation. One canonical grammar kills the triplicate definitions, unifies the two incompatible applyRecords (snapshot fold vs live applier), makes sparse-array producers and ordered projections remotely reconstructible, and recovers fero's clone tax — while keeping the zero-alloc hot path as an explicit profile rather than an accident.
- **Implicit subscription lifecycle + unobservable cascade timing: WeakRef sinks with no detach, and emissions carrying no write-origin**
  - why: Sinks are WeakRef-held with no public detach and FunctionSink back-refs only its fn, not its source (core.ts:211, :1201; :839). Verified consumer damage: fero must pin BOTH the sink host and the served source proxy per subscription or a derived projection GC's its filter→op chain and freezes the stream (dispatch.ts:100-114), and must latch a `destroyed` boolean because a write after teardown would otherwise still commit and fsync (resource/index.ts:871-875). Worse, a sink cannot distinguish 'echo of my own inbound apply' from 'genuine local write' except by boolean flags timed against data's internal drain order — data commit c870bde (deferring re-entrant writes to a `_pending` drain) silently converted fero's `applying` guard into a deterministic cluster-wide LOST WRITE (DECISIONS Z:1385-1400). The current fix (the `discarding` partition Set, index.ts:892-900) survives the present drain order only; there is no versioned timing contract. Provenance would have to thread through every mutation path and every sink dispatch — cross-cutting, not a patch.
  - redesign: First-class subscription handles: connect returns a disposable with strong retention and synchronous detach (fero M0 items 3, plan-v3.md:459-460), keeping WeakRef auto-unsubscribe as an opt-in ergonomic mode. Thread a write token/origin through the cascade so echo suppression is declarative (`if (rec.origin === me) return`) instead of timing-dependent boolean gymnastics, and publish a versioned re-entrancy/ordering contract with cross-repo CI contract tests — eliminating the entire c870bde failure class.
- **Closures are the primitive in operator argument slots; the serializable IR is a bolt-on that can never see closure-form code**
  - why: Operators store raw closures, so: filter/map/length/group have no matches() and CANNOT dedup (two equal closures are never ===; even the same reference makes two views — dir.ts:29-37, README.md:66-71); app code written in closure form is unserializable, so fero's distribution stops at 7 hand-coded aggregates with specOf→null → console.warn + a silently-LOCAL wrong-scoped answer (dispatch.ts:375-410, 433-448 — the failure mode plan-v3.md:444-446 explicitly rejects); and capability classification is hand-maintained name sets that already drifted (BUILTIN at dispatch.ts:359 omits `get`, added to data for Option B — a `data.get(...)` on a scoped facade is misread as a partition key today). The prototype proves byte-identical parity is achievable (compile-to-natural-JS-op, 15 parity tests + 20,000-step fuzz + adversarial audit, README.md:57-79), but PLAN.md:167-169 defers the actual inversion (operators storing `.node`, `pred(ExprNode)` arg slots) precisely because retrofitting it means touching all 16 operators' constructors, matches(), dispatch, and perf gates simultaneously — rewrite-shaped work.
  - redesign: Invert the layering: every operator natively stores its serializable node; the closure form becomes sugar that compiles TO the IR (with genuinely opaque fns as an explicit Tier-3 escape hatch, as the proto already scopes). Deep-equal matches() dedup for filter/map/length/group falls out for free; capability descriptors derive from the registry instead of hand-sets (new ops auto-classify, closing the silent-misclassification class); plans serialize without a bolt-on layer; and fero's L3 planner becomes a pure dIR→dIR transform + per-holder rehydrate — far more than 7 aggregates distribute, with typed errors instead of warn+wrong-answer.

## Competitive landscape (2026)

### TC39 Signals proposal (status + semantics)
- state of art: Still Stage 1 (since April 2024, unchanged into 2026; https://github.com/tc39/proposal-signals). Design: Signal.State (writable, custom equality) + Signal.Computed (LAZY — recomputes only on read; MEMOIZED — caches unless deps actually differ; GLITCH-FREE by pull). Auto-tracking of dependencies during evaluation. Signal.subtle.Watcher is the framework hook: synchronous dirty notification in which 'no signals may be read or written' — deliberately forcing effect SCHEDULING out of the core. Deliberately excluded: effects, async, transactions. Advancement gated on production polyfill + integration into Vue/Solid/Svelte/Angular; signal-polyfill (https://github.com/proposal-signals/signal-polyfill) is explicitly preview, not production-recommended. Svelte 5 runes are described as trivially compilable to this API; Lit ships @lit-labs/signals against the polyfill (https://lit.dev/docs/data/signals/).
- relevance: data's scalar layer (a ViewProxy wrapping one value, .to() derivations, aggregates emitting scalar VPs) is exactly the shape the proposal standardizes — but data is EAGER-push, the opposite of the proposal's lazy/memoized/glitch-free computeds. The proposal's collection story is nonexistent: Z-set/delta pipelines (data's real differentiator) are out of scope, so alignment is an interop-boundary concern, not an architecture constraint.
- adopt/avoid: ADOPT the semantics (lazy memoized computeds, auto-tracking, watcher-style 'notify but don't run' scheduling hook, custom equality) and keep the scalar read/write surface trivially adaptable to Signal.State/Computed (a toSignal()/fromSignal() bridge). AVOID betting the API on the proposal itself (Stage 1, could change or stall for years) and AVOID shipping effects that run synchronously inside notification — every serious design now schedules.

### Fine-grained framework convergence (Solid 2.0, Svelte 5, Vue 3.6/Vapor, Preact, alien-signals)
- state of art: Total convergence on PUSH-PULL: writes push only a dirty flag through the graph; deriveds recompute lazily on read, with referential-equality cut-off skipping downstream work (Svelte 5 $derived docs: https://svelte.dev/docs/svelte/$derived; alien-signals: https://github.com/stackblitz/alien-signals). Glitch-freedom via graph coloring / height ordering solves the diamond problem (Reactively write-up: https://dev.to/milomg/super-charging-fine-grained-reactive-performance-47ph; Leptos appendix: https://book.leptos.dev/appendix_reactive_graph.html). Vue 3.6 ported alien-signals (doubly-linked-list dependency edges, iterative not recursive propagation) for ~4x Vue 3.4's reactivity throughput, 30x+ on many-computed-reads-after-write (https://github.com/vuejs/core/pull/12349). Vue Vapor is stable in 3.6: SFCs compile to direct DOM ops, no VDOM, opt-in per component, 100k components ~100ms (https://github.com/vuejs/vue-vapor). Solid 2.0 beta: FIRST-CLASS ASYNC — memos can return promises, the graph handles suspension/resumption, deterministic batching, plus action()/createOptimistic for mutations; sync-read-after-write can now observe stale values by design (https://www.infoq.com/news/2026/05/solidjs-2-async/, https://github.com/solidjs/solid/discussions/2596). Ownership: Solid's owner tree (createRoot/onCleanup, children disposed on parent re-run) is the model everyone copies (https://docs.solidjs.com/reference/reactive-utilities/create-root).
- relevance: data's eager depth-first push with no lazy memos, no equality cut-off, no topological scheduling, and no ownership tree is off-consensus on every axis for its SCALAR/derivation layer. Its collection operators are a different regime (delta pipelines are inherently push, like IVM engines), but the scalar reads (aggregates, .to(), reactive operator args) and the DOM effect layer would benefit directly from lazy pull + scheduled flush. Vapor also proves the no-vdom renderer thesis data bet on — but with compiler backing.
- adopt/avoid: ADOPT: push-dirty/pull-value for scalar deriveds; equality cut-off; graph-coloring or height-based glitch-free scheduling for effects; batch-and-flush effect queue (one DOM commit per turn/frame by default); an explicit owner/scope tree with onCleanup. ADOPT (design for, even if v3.0 defers): an async story — Solid 2.0 makes promise-aware derivations and optimistic mutation table stakes. AVOID: eager synchronous fan-out per write (the current model) as the default; it is both slower (diamond re-runs, no memo skip) and glitchy relative to every 2026 peer.

### IVM theory — DBSP/Z-sets, differential dataflow, and whether it subsumes the 13-verb protocol
- state of art: DBSP (VLDB 2023 best paper; Feldera: https://www.vldb.org/pvldb/vol16/p1601-budiu.pdf) models every relation as a Z-SET (rows weighted by integers; +1 insert, −1 delete; update = retract+insert) and every operator as a function on Z-set streams. The algebra is CLOSED: all operators consume and produce Z-sets 'with no exceptions', so incrementalization is mechanical (lift, differentiate/integrate, chain-rule composition) and composition of any operators is correct by construction. Differential dataflow/Materialize generalize with multi-dimensional timestamps (https://materialize.com/blog/life-in-differential-dataflow/), but the client-side TS ports found that unnecessary: d2ts (https://github.com/electric-sql/d2ts) → d2mini → @tanstack/db-ivm progressively REMOVED multi-dimensional versioning and frontiers ('without the complexities of multi-dimensional versioning' — https://www.npmjs.com/package/@electric-sql/d2mini). Known hard spot: Z-sets are UNORDERED — ORDER BY/top-k must be modelled as a special ordered aggregate/index, acknowledged as non-trivial (https://news.ycombinator.com/item?id=41951542, DBSP paper §window/topk). TanStack DB proves the approach ships in JS: live joins/filters/aggregates updating sub-millisecond over 100k+ rows, ~0.7ms per update to a sorted 100k collection (https://tanstack.com/blog/tanstack-db-0.1-the-embedded-client-database-for-tanstack-query).
- relevance: This is the direct answer to the C1..C16 bug family. Those bugs (array splice-shift vs hole, sparse `undefined` slots, BR1A/BI0A/BH1/BF0 pairwise operator conformance, window-rotation emission order) all stem from an OPEN protocol: 13 verbs where each operator×verb×source-shape combination is hand-written and any miss is a silent desync — the repo's own history (differential harness, KNOWN_FAILURES, residual C14/C16) is the empirical cost. A Z-set core has ONE delta shape (keyed row, weight), so filter/group/aggregate/set-algebra compose closed — the entire positional/sparse conformance matrix disappears. Caveats mapping to data's features: (1) ordering/pagination (az/za/top/limit) does NOT come free — it must be a dedicated ordered-index operator at the edge (exactly where data's hardest bugs live anyway, and where TanStack's ~0.7ms sorted-update shows a keyed B-tree-ish index works); (2) in-place nested mutation (BU2) has no Z-set analog — update must become retract(old)+insert(new), which REQUIRES the old value (nb: data's own reduce already hit this wall — its BU2 rebuild fallback); (3) array-positional semantics should be dropped from the CORE and reconstructed at the DOM edge via keyed rows + ordering.
- adopt/avoid: ADOPT: a weighted keyed-delta (single-time Z-set) core algebra as the internal protocol; treat update as retract+insert with old-value capture (favor immutable row discipline or copy-on-write at the proxy boundary); one dedicated ordered-view operator (sorted index + windowing) implementing top-k/pagination, emitting keyed+position deltas only at the sink boundary. ADOPT d2mini's lesson: skip timestamps/frontiers — single-version, synchronous-batch semantics suffice client-side. AVOID: porting the 13-verb positional/sparse protocol into v3 (it is the proven bug generator); AVOID full differential-dataflow timestamps (complexity with no client-side payoff); AVOID losing the O(1) in-place BU2 fast path blindly — benchmark retract+insert vs the current mutating path on the swarm/patch workloads before committing, since that fast path is a flagship perf story.

### Analytics-in-browser interop (DuckDB-WASM, Mosaic/vgplot, Arrow, Arquero)
- state of art: Mosaic + DuckDB-WASM is the reference architecture for large-N interactive analytics: cross-filtering 10M rows in-browser (billions server-side) by compiling interactions to SQL over PRE-COMPUTED DATA-CUBE INDEXES per interaction, not raw-row scans (https://github.com/uwdata/mosaic, https://observablehq.com/@uwdata/mosaic-cross-filter-flights-10m, TVCG paper https://idl.cs.washington.edu/files/2024-Mosaic-TVCG.pdf). Apache Arrow IPC is the interchange: 'efficient serialization of query results with no subsequent parsing overhead', zero-copy columnar buffers aligned for SIMD (https://arrow.apache.org/js/). Arquero covers array-backed dataframe transforms over Arrow columns (https://github.com/uwdata/arquero). WASM relaxed SIMD is now on by default in Chrome 114+ and Firefox 145 (Safari still flagged) (https://caniuse.com/wf-wasm-simd-relaxed, https://webassembly.org/news/2026-01-21-states-of-wasm/).
- relevance: data's crossfilter benchmarks (231k flights) sit an order of magnitude below where Mosaic operates, and the dIR columnar-WASM-SIMD prototype is a step toward that regime. The strategic insight from Mosaic is that at large N the winning move is precomputed aggregates (data cubes) + columnar transport, not faster row-at-a-time delta propagation; data's edge is the opposite end — per-row surgical reactive updates to live DOM, which Mosaic/DuckDB do not do.
- adopt/avoid: ADOPT: Arrow (Table / RecordBatch, IPC) as the columnar interop format for the dIR/WASM path — zero-copy into SIMD kernels, free interop with DuckDB-WASM/Arquero/Mosaic as SOURCES feeding data's reactive edge; design source adapters so a DuckDB-WASM query result or an Electric/Tanstack sync stream can be a first-class collection source. CONSIDER data-cube-style precomputed group-by indexes for the crossfilter workload (it is what makes 10M-row brushing possible). AVOID: competing with DuckDB-WASM on raw scan/aggregate throughput as the headline — a SQL engine with data cubes wins at scale; position the WASM kernels as accelerating the delta pipeline, not as a query engine.

### Disposal and ownership (WeakRef/FinalizationRegistry vs explicit scopes)
- state of art: Ecosystem consensus is unambiguous: GC-driven cleanup is a safety net, never the primary mechanism. TC39's own WeakRef proposal warns cleanup 'may happen much later than expected, or not at all' and to use these 'as a backstop against certain bugs, rather than as a normal way to clean up' (https://github.com/tc39/proposal-weakrefs); Cloudflare shipped FinalizationRegistry and titled the post 'why you should never use it' (https://blog.cloudflare.com/we-shipped-finalizationregistry-in-workers-why-you-should-never-use-it/); MobX explored FinalizationRegistry for reaction disposal and did not make it primary (https://github.com/mobxjs/mobx/discussions/2562). The positive model is Solid's ownership tree: computations created under an owner are disposed when the owner re-runs or its root's dispose() is called; onCleanup hooks; unowned roots are documented as leak hazards (https://docs.solidjs.com/reference/reactive-utilities/create-root, https://docs.solidjs.com/reference/lifecycle/on-cleanup).
- relevance: data holds sinks via WeakRef (core.ts:421 per its docs) — the documented consequence is silent unsubscription when the consumer drops its only strong ref, which the repo's own tests must work around by keeping connect([]) returns alive in locals. That is precisely the failure mode the field warns about: correctness (does my view keep updating?) depending on nondeterministic GC.
- adopt/avoid: ADOPT: explicit ownership — every derived view/effect is created under a scope/owner; disposing the owner detaches the whole subtree deterministically; render() creates an owner per mounted root tied to DOM disconnection; dispose()/Symbol.dispose (`using` declarations) on every view. KEEP WeakRef/FinalizationRegistry only as a leak-detection backstop (dev-mode warning when an undisposed view is collected). AVOID: any semantics where GC timing changes observable behavior — it is untestable and now reputationally a known anti-pattern.

### Direct competitor: TanStack DB (+ Electric local-first sync)
- state of art: TanStack DB is 'the embedded client database for TanStack Query': typed local collections, cross-collection LIVE QUERIES (joins, filters, aggregates) maintained by differential dataflow (its in-tree @tanstack/db-ivm, descended from d2ts/d2mini), optimistic transaction mutations, and query-driven sync (0.5, with ElectricSQL; FOSDEM 2026 talk). Sub-ms incremental updates over 100k+ rows; ~0.7ms single-row update in a sorted 100k collection on an M1 Pro; 1.0 targeted Dec 2025 (https://tanstack.com/db/latest, https://tanstack.com/blog/tanstack-db-0.5-query-driven-sync, https://electric-sql.com/blog/2025/07/29/local-first-sync-with-tanstack-db). It ships framework adapters (react-db etc.) and rides the TanStack brand/distribution.
- relevance: This is the closest thing to 'data v3' already shipping: incremental collection queries in TypeScript with a closed delta engine underneath. Its gaps are data's opportunities: no built-in renderer (it feeds React/etc. re-renders at the component boundary rather than per-key DOM surgery), a query-builder API rather than chainable proxies over plain objects, no columnar/WASM acceleration, and its IVM is generic rather than tuned per-operator (data's per-operator benchmarks may still beat it on hot paths like windowed sort).
- adopt/avoid: ADOPT: benchmark v3 against TanStack DB (not just crossfilter/MobX/React — the 2026 peer set changed); consider joins (data has none; TanStack leads with them) and an optimistic-mutation/transaction story; make sync streams (Electric shapes, WebSocket feeds) first-class sources. AVOID: shipping v3 as a query engine WITHOUT the renderer story — head-to-head on 'reactive client DB' alone, TanStack wins on ecosystem; data's defensible combo is delta-engine + surgical no-vdom DOM sink + O(delta) all the way to the paint.

### Proxy-based API ergonomics and known traps (Vue reactive, Solid stores, data's ViewProxy)
- state of art: The field has fully documented proxy-store traps: destructuring/aliasing severs reactivity (Vue toRefs/storeToRefs exist solely to patch this — https://vuejs.org/guide/essentials/reactivity-fundamentals.html); proxy-vs-raw identity hazards (=== fails across the boundary, mixing raw and proxied copies corrupts logic — https://vuejs.org/guide/extras/reactivity-in-depth); Solid answers with READ-ONLY store proxies plus a path-based setStore writer, separating read tracking from writes. Vue 3.6 keeps the proxy DX but swapped the engine underneath (alien-signals). Nobody else makes proxies CALLABLE or thenable; data's `await proxy` thenable-assimilation guard and `proxy.value`-vs-`proxy[value]` footgun are self-inflicted instances of this trap class.
- relevance: data's DX bet (plain-object mutation, chainable operators off the proxy) is validated by Vue/Solid keeping proxies — but its specific choices (callable proxy, Symbol-keyed raw access, child-view-on-any-property-read so `.value`/`.then` collide, typed-write vs runtime-write divergence in Option B) sit in the documented footgun zone the incumbents engineered away.
- adopt/avoid: ADOPT: Solid's split — reads through a (non-callable) tracking proxy, writes through explicit methods (update/patch/remove already exist in v2's Option B; make them THE only write path, runtime included, so types and runtime agree); reserve a small non-colliding read surface (.get(key), peek()/raw via one well-known symbol or method, not property magic). AVOID: callable/thenable proxies, property-name collisions (`value`, `then`, `constructor`), and any API where destructuring silently loses reactivity without a lint/dev-mode warning.

### Scheduling, effects, and async resources (what a 2026 core must also have)
- state of art: Glitch-free scheduling is a solved problem with known algorithms: height-based priority queues (FrTime/REScala lineage — https://soft.vub.ac.be/Publications/2012/vub-soft-tr-12-13.pdf) and the graph-coloring lazy-marking approach used by Reactively/Solid/alien-signals (https://dev.to/milomg/super-charging-fine-grained-reactive-performance-47ph). Effects are universally batched and scheduled (microtask or frame), never run inline during write propagation; TC39's Watcher API structurally enforces this. Async is the current frontier: Solid 2.0 threads promises through the graph with suspension, deterministic batching, action()/optimistic primitives; TC39 punts on it; TanStack DB handles it as sync/transactions at the collection layer.
- relevance: data currently interleaves user-observable effects with eager propagation (tap fires mid-cascade; the flow essay's transient-undefined-during-repoint gotchas, and the chat/library defensive-binding discipline, are user-visible glitch states the examples must code around). A v3 with proper topological/batched delivery would delete that whole gotcha category (bindings would never see a mid-cascade transient).
- adopt/avoid: ADOPT: two-phase commit per batch — propagate deltas/dirty marks, then flush sinks once in dependency order (the existing patch() batching generalized to ALL writes); document sync-read semantics explicitly (read-your-writes within a batch or not — Solid 2.0 chose staleness, TC39 chose consistency via pull; pick pull). ADOPT a minimal async-source primitive (a collection fed by a promise/stream with pending/error states) even if full Suspense-like orchestration is out of scope. AVOID: delivering per-row events synchronously mid-cascade to user callbacks by default (the transient-undefined class of bugs); AVOID inventing a novel scheduler when height/coloring algorithms are proven and small.

### Biggest lessons
- The 2026 field has one consensus reactive core for scalars — push dirty flags, pull values lazily, memoize with equality cut-off, schedule effects glitch-free (TC39 Signals, Svelte 5, Vue 3.6/alien-signals, Solid, Preact all converged) — and data's eager depth-first push is off-consensus on every axis; a rewrite should adopt push-pull for the scalar/effect layer while keeping push-based delta pipelines for collections, which is exactly how IVM engines work.
- A closed delta algebra (single-time Z-sets: keyed rows with integer weights, update = retract+insert) makes operator composition correct BY CONSTRUCTION and would dissolve the entire C1..C16 positional/sparse conformance bug family, which exists precisely because the 13-verb protocol is open (every operator must hand-implement every verb × source-shape combination); the residual hard parts are exactly ordering/top-k (unordered algebra needs a dedicated ordered-index operator at the edge) and in-place mutation (needs old-value capture) — d2mini/@tanstack/db-ivm proved client-side JS needs none of differential dataflow's timestamp machinery.
- The competitive frame changed: the 2026 peer to beat is TanStack DB (differential-dataflow live queries with joins, sub-ms over 100k rows, optimistic mutations, Electric sync, TanStack distribution) at the data layer and Vue Vapor/Solid compilers at the no-vdom render layer — data's only defensible position is the vertically-integrated combination (closed delta engine + per-key surgical DOM sink + optional Arrow/WASM columnar acceleration), because each pillar in isolation now has a stronger incumbent.
- GC-driven lifecycle (WeakRef-held sinks) is now a documented anti-pattern (TC39's own guidance, Cloudflare's 'never use it', MobX's rejection); every serious library uses explicit ownership scopes with deterministic disposal, keeping finalizers only as dev-mode leak detectors.
- Interop targets are clear and cheap to hit: Arrow IPC/Tables for columnar data (zero-copy into WASM SIMD kernels, free interop with DuckDB-WASM/Mosaic/Arquero as large-N sources), and a Signal.State/Computed-shaped bridge for scalar interop with the eventual TC39 standard — while the proxy API itself should adopt Solid's read-proxy/explicit-writer split and drop callable/thenable/property-collision magic.

### Threats
- TanStack DB ships today what v3 would promise (incremental live queries incl. joins, sub-ms on 100k+ rows, ~0.7ms sorted-collection updates, optimistic transactions, sync) with TanStack-scale distribution and a Dec-2025 1.0 — a v3 that is 'only' a faster operator set without joins/sync/persistence arrives outcompeted on features and ecosystem.
- Rebuilding on a Z-set core could regress data's flagship benchmarks: retract+insert per update forgoes the current O(1) in-place BU2 fast path and per-operator tuned hot loops (the per-op BENCHMARK.md wins), so v3 could be more correct but measurably slower than v2 — and than TanStack's db-ivm — on the exact workloads the landing page advertises, unless the mutation path is benchmarked before the algebra is locked.
- Keeping the bespoke 13-verb protocol instead is the opposite trap: the C14/C16 residuals and the differential-harness history show the conformance matrix generates bugs indefinitely, and every new operator multiplies it — v3 inherits an unbounded correctness tail no competitor pays.
- At large N the analytics niche is already owned: DuckDB-WASM + Mosaic cross-filters 10M+ rows via data-cube indexes and Arrow transport, so the dIR columnar/WASM story competes with a full SQL engine and a research-lab architecture; positioning the WASM kernels as a query engine (rather than accelerating the reactive delta edge over Arrow inputs) is a losing fight.
- TC39 Signals plus compiler-backed no-vdom renderers (Vue Vapor stable, Solid 2.0, Svelte 5) are commoditizing both the scalar reactivity substrate and the surgical-DOM layer; a hand-rolled callable-proxy core with builder/JSX sinks and no standard-signal interop risks being obsolete-on-arrival at both boundaries, while its proxy magic (thenable, `.value` collision, destructuring loss) sits in the trap class incumbents engineered away.
- Async/local-first is table stakes in 2026 (Solid 2.0 first-class async + optimistic primitives, TanStack/Electric query-driven sync); a purely synchronous in-memory v3 with no promise/stream/sync source story will read as dated regardless of raw speed.
- Standards risk cuts both ways: TC39 Signals is still Stage 1 and its polyfill is non-production — deep-aligning v3's core to the proposal's exact API could strand it if the proposal changes, while ignoring it entirely forfeits the interop story; the safe posture is semantic alignment plus a thin bridge.
- WeakRef-based disposal is now reputationally radioactive (Cloudflare's 'never use it'); carrying it into v3 would be an immediately citable architectural defect versus every incumbent's explicit ownership model.

### The 5 hardest open design questions
- STORAGE & ROW IDENTITY: What is v3's native store — a keyed row store (stable synthetic keys for array sources + a separate order/rank channel, per the core/protocol/operators audits), columnar typed-array storage with validity bitmasks (per the verified 63-500x headroom in experiments/wasm/results-altbackend.md), or a designed hybrid (keyed row store as the identity/nesting substrate with per-source maintained hot columns for the batch-recompute frontier)? Sub-questions the audits leave open: where synthetic keys are minted and whether they survive the wire; how ordering/top-k works over an unordered keyed algebra (the acknowledged Z-set hard spot — one dedicated ordered-index operator at the edge?); and whether the transparent nested-mutation DX (`proxy.a.b.c = 1` cascading, per-row child-view identity) can be materialized over columns without giving back the wins.
- DELTA ALGEBRA & THE COMPATIBILITY LINE: What is the exact canonical delta — does update carry oldValue natively (closing P3/C5/C7 by design), and is an update a first-class verb or retract+insert? Which of the HARD emission invariants survive verbatim (no-phantom-events, rotation-emits-updates, removes-before-fills-or-atomic-batches, snapshot-then-deltas-on-connect) and which are explicitly version-broken? And precisely how is fero's ChangeRecord wire shape { type, key: string[], value, at? } derived from the new algebra — a lossless compat profile, an additive oldValue/move extension under SCHEMA_VERSION, or a breaking v2 shim with a sunset date? This decision gates fero, every test, the flow essay, and the benchmark corpus simultaneously.
- SCHEDULING & CONSISTENCY CONTRACT: Does v3 keep synchronous read-after-write per mutation (what every committed benchmark tick, example, and fero's write-capture assume), adopt two-phase batch commit with one flush per turn/frame (deleting the transient-undefined gotcha class and the emission-order theorems), or split the model (push deltas through collections synchronously, pull scalars lazily with equality cut-off a la 2026 consensus)? Corollaries that must be answered together: the glitch-freedom mechanism (height/coloring vs topological batch), where user effects run (never mid-cascade?), the versioned re-entrancy/timing contract fero's M0 demands (the c870bde lost-write class), and the explicit plan to re-baseline or dual-publish the benchmark corpus when the settle semantics change.
- PUBLIC API SURFACE & LIFECYCLE: Is the callable/thenable ViewProxy retained (with cached wrappers and honest reflection traps) or replaced by a non-callable read proxy + methods-only write path — closing the three-namespace collision (data keys vs operators vs built-ins), the types-reject/runtime-accepts rift, and the destructuring/thenable trap class the incumbents engineered away? And what is the lifecycle model: explicit owner scopes with disposable subscriptions as primary (deterministic dedup, removeEventListener, render dispose) with WeakRef demoted to a dev-mode leak backstop — while still preserving the zero-ceremony 'drop it and it's gone / hold the DOM and it lives' DX for script-tag consumers? The dedup key design (operator class + normalized IR args + bound-view identity, with opaque-fn freshness preserved) hangs off this same decision.
- SCOPE & THE SEAM AS DESIGN CENTER: Is the serializable ExprNode IR the PRIMARY operator-argument representation (closures compile to it; opaque fns are a documented escape hatch) given CSP constraints on new Function, the deliberately excluded operators (to/reduce/tap), and the ergonomics cost — and is the SourceBacking kernel boundary + fero's four M0 contract items the design center of v3 or an adapter layer bolted on later (fero's stated fallback is wrap-or-fork, i.e. losing the flagship consumer)? Entangled with this: the competitive scope question the landscape forces — does v3 answer TanStack DB by adding joins, optimistic mutations/transactions, and first-class async/sync sources, or does it stay an operator engine whose defensible position is the vertically-integrated combo (closed delta engine + keyed surgical DOM sink + Arrow/columnar acceleration)? The renderer's keyed reconciliation and ownership tree must be co-designed with whichever answer is chosen, since keyed DOM identity requires the core protocol to carry stable row keys.
