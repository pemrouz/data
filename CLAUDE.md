# CLAUDE.md

Guide for Claude sessions working in this repo. Read this before making changes.

## What this is

A small TypeScript reactive data library. `$(value)` wraps a value or array into a `ViewProxy`; chainable operators (`filter`, `between`, `gt`/`lt`/`gte`/`lte`, `az`/`za`/`top`/`limit`, `length`, `sum`/`avg`/`max`/`min`, `some`/`every`, `intersect`/`union`/`except`, `group`/`distinct`, `map`/`to`/`reduce`, `tap`, `keys`/`values`, `reverse`) produce derived reactive views; [render/index.ts](render/index.ts) attaches reactive data to the DOM via `HTML.*`/`SVG.*` builders. JSX authoring is supported via [jsx/index.ts](jsx/index.ts) (`h`, `Fragment`, `For`), re-exported from `data/full`. Inspection helpers live behind the opt-in `data/devtools` entry — see [devtools/README.md](devtools/README.md).

## Source layout and build

`.ts` files at the root and under `operators/`, `render/`, `jsx/`,
`devtools/`, `tests/` are the source of truth. `.gitignore` blanket-ignores
`*.js`; build output goes to `dist/` (gitignored). There are **no committed
`.js` siblings of `.ts` sources** — that scheme was retired. A handful of
hand-written `.js` files remain in tree (e.g.
[assets/landing.js](assets/landing.js), `examples/crossfilter/flights*.js`)
because they have no `.ts` counterpart. (The old `render/render.test.js`
stub — four empty tests and console noise — was deleted; real render unit
coverage lives in [render/list.test.ts](render/list.test.ts) and
[render/devtools_link.test.ts](render/devtools_link.test.ts), plus the
Playwright specs.)

`tsup` produces eight sub-path entries that line up 1:1 with the `"exports"`
map in [package.json](package.json):

| Sub-path                | Source       | What it ships |
|---|---|---|
| `data`                  | [index.ts](index.ts)                          | **Default entry.** Core (`$`, `value`, `render`, `HTML`, `SVG`, `Operators`, `createOperator`) **plus every operator registered** on the dispatch table — `proxy.filter(...)` works the moment you import `$`. This is the entry consumers (and generated code) should reach for. |
| `data/lean`             | [lean.ts](lean.ts)                            | Registration-free core: the same exports as `data` *minus* the operator dispatch side effect. Pick this only to tree-shake operators you don't use (and register a subset onto `Operators` yourself, or call the function-style operator API). Calling `.filter(...)` on a `data/lean` proxy throws, pointing back at `data`. |
| `data/full`             | [full.ts](full.ts)                            | Strict superset of `data` — everything in the default entry plus the JSX helpers (`h`, `Fragment`, `For`, `jsx`, `jsxs`, `jsxDEV`). Import this only when you author views in JSX. |
| `data/render`           | [render/index.ts](render/index.ts)            | Just the DOM render layer (`render`, `HTML`, `SVG`). |
| `data/devtools`         | [devtools/index.ts](devtools/index.ts)        | Opt-in inspection helpers — importing this attaches `$.inspect`, `$.graph`, `$.fromDOM`, `$.highlight`, `$.trace`, `$.profile`, `$.cascades` onto the canonical `$`, AND lazy-loads + auto-mounts a graph-first right-edge overlay panel ([devtools/panel/index.ts](devtools/panel/index.ts)). The panel has a Tree/DAG layout toggle, a slide-in inspector with three tabs (Inspect / Events / Profile), a DOM picker (◎), Alt-hover badges (⊙ or hold Alt), and a draggable left-edge resize handle (width persisted to `localStorage` under `data-devtools-dock-width`). Append `?nopanel` to the URL to suppress the panel; `$.devtools.panel.{open(proxy?), close(), shell}` for explicit control / reaching into the closed shadow root from tests / console. |
| `data/jsx-runtime`      | [jsx-runtime.ts](jsx-runtime.ts)              | Automatic JSX runtime entry — `jsx`, `jsxs`, `Fragment`. Picked up when a consumer sets `"jsxImportSource": "data"` in their tsconfig. Same NodeProxy/DOMSink semantics as the classic `h` transform. |
| `data/jsx-dev-runtime`  | [jsx-dev-runtime.ts](jsx-dev-runtime.ts)      | Dev-mode counterpart — `jsxDEV`, `Fragment`. |

Tests do **not** require a build: `node --experimental-strip-types` reads
`.ts` directly. Run `npm test`. Examples *do* require a build because they
import from `dist/` via an import map; `npm run serve` chains `tsup` (and a
small `tsc` pass for the JSX example projects via `build:examples-jsx`)
before the static server.

JSX projects extend a single shared [tsconfig.jsx.json](tsconfig.jsx.json)
(jsx: react, jsxFactory: h, jsxFragmentFactory: Fragment) — both example
dirs ([examples/todo-jsx/tsconfig.json](examples/todo-jsx/tsconfig.json),
[examples/crossfilter-jsx/tsconfig.json](examples/crossfilter-jsx/tsconfig.json))
and [jsx/tsconfig.json](jsx/tsconfig.json) just `extends` it. New JSX
sub-projects should follow the same pattern rather than duplicating the
compilerOptions.

## Commands

From [package.json](package.json):

| Command | What it does |
|---|---|
| `npm test` | Runs `*.test.ts` via `node --experimental-strip-types --test` |
| `npm run perf` | Runs `*.perf.ts` (median-of-5 timing assertions) via [perf/run-gate.mjs](perf/run-gate.mjs), which globs every `*.perf.ts` under `index`/`operators`/`render`/`devtools`/`comparisons`/`perf` — **`experiments/` is deliberately excluded** (experimental, ungated). New perf files in gated roots are picked up automatically. The shared timer is [perf/measure.ts](perf/measure.ts) (`gateMeasure` lean / `benchMeasure` warm). **Each operator's workload (source builder + setup/single/batch closures + each closure's gate threshold) lives ONCE in [perf/workloads.ts](perf/workloads.ts) — "Mode A".** The gate `operators/<op>/<op>.perf.ts` is a thin driver that loops `Object.entries(<op>.workloads())` and asserts `ok(gateMeasure(w.run, w.reps) < w.gate)`; the report sweep [perf/run-report.ts](perf/run-report.ts) re-measures the SAME closures with `benchMeasure`. So a report row can never be a number no gate asserted — the old parallel `{v,g,w}` uniform sweep was retired once the last operator migrated. A workload case may carry `reps` (non-default sample count, for source-consuming churn) and bundles every graph piece on `keep` (sources + bounds + view) so a multi-source / reactive-bounds op isn't GC'd mid-measurement. A batch case that re-touches the same keys must vary them each rep (alternate a base / distinct keys) or it dedups to a ~0ms no-op. `aggregate.perf.ts` is hybrid: it drives its timing cases from `workloads.ts` but keeps its two deterministic projector-COUNT guards inline (count assertions, not timing). The collated report lands in `perf/perf.json` (+ `perf/history.jsonl` trend) via `npm run perf:report`; the dashboard ([perf/index.html](perf/index.html) + [perf/main.js](perf/main.js), itself a `data` app) is served at **`/perf/`** on GitHub Pages. The report nests harnesses: **ops** (every operator's gate workload), **H1** complexity (deterministic op-count per insert — O(1) vs O(N), from [perf/run-report.ts](perf/run-report.ts) `h1Complexity`), **H4** interactive tail (synthetic crossfilter brush), **H6** self-regression (advisory: flags an ops row that crept ≥1.5× past its own 3σ vs history — non-gating), **H7** cross-library (data's single-tick speedup vs 8 peers, parsed from the committed `operators/<op>/BENCHMARK.md` tables by [perf/gen-h7.mjs](perf/gen-h7.mjs) → `perf/h7.jsonl`, injected by `gen-report.mjs`; refresh on the BENCHMARK.md cadence: `npm run bench:ops` → `_gen-bench-md.mjs` → `npm run perf:h7`, NOT per sweep since the peer suite takes minutes). |
| `npm run test:render` | Playwright e2e against `examples/` |
| `npm run serve` | `tsup` build + static server on `:3000` for examples |
| `npm run build` | `tsup` → `dist/` (ESM + per-entry `.d.ts`) |
| `npm run test:all` | Both unit and Playwright tests |

## Public API

- `$(value)` → `ViewProxy`. Read raw value with `proxy[value]` (the `value` Symbol from [core.ts:4](core.ts#L4)). Mutate via assignment: `proxy.foo = 1`, `proxy[2].completed = true`, `delete proxy[1]`, `proxy[value] = newValue`.
- Operators chain off the proxy: `data.filter(d => d.active).between('val', [0, 100]).length()`. The chainable form requires the dispatch table to be populated, which happens automatically when you import from `data` (the default entry, [index.ts](index.ts)) or `data/full`. The registration-free `data/lean` entry ([lean.ts](lean.ts)) leaves the table empty; calling `.filter(...)` on a proxy sourced from `data/lean` throws an error pointing the user back at `data`. The canonical dispatch list lives in [register.ts](register.ts) — a side-effect-only module imported by [index.ts](index.ts) (and, transitively, by `data/full`). The dispatch picks a class based on argument shape (e.g. `filter(fn)` → `FilterValue`, `filter('key', val)` → `FilterStringValue`, `filter({k:v})` → `FilterObjectValue`).
- `render(el, template)` from [render/index.ts](render/index.ts); `HTML.div(...)`, `SVG.path(...)` builders.
- `h(tag, props, ...children)`, `Fragment`, `For` from [jsx/index.ts](jsx/index.ts) (re-exported by `data/full`) — JSX adapter over the same builders. `<div className="x">{c}</div>` desugars to `h("div", {className:"x"}, c)` which returns the same `NodeProxy` AST `HTML.div.x(c)` produces. Same `render()`, same `DOMSink`, same per-key surgical updates. ViewProxy children with no function sibling route through `.text()` (preserves element identity); with a function sibling they stay on the data path so `[VP, fn]` keeps working as a data-iteration shorthand.
- `connect` is built-in (not an operator): `proxy.connect([])` returns the array and pushes change events into it; `proxy.connect(obj, 'prop')` mirrors the value to `obj.prop`; `proxy.connect(obj, fn)` calls `fn(change)` on each event. There is **no single-arg `connect(fn)` form** — a bare function can't act as a sink (it has none of the protocol verbs), so it throws immediately at `connect()` time with a message pointing at the two-arg `connect(anchor, fn)`. See [core.ts:1112](core.ts#L1112).
- `raf` is built-in (not an operator): `const write = proxy.raf()` returns a coalescing writer. `write(v)` schedules one `requestAnimationFrame` that commits the latest pending value to `proxy[value]`; subsequent calls before the frame fires overwrite the pending value. `write.flush()` commits immediately and cancels the pending frame — for `pointerup` handlers that want the final position to land without an extra frame's latency. Falls back to `setTimeout(cb, 16)` outside the browser. See the `raf` helper near the bottom of `core.ts`.
- `first` / `last` are built-ins (not operators): `proxy.first()` / `proxy.last()` return the child ViewProxy at the source's first / last key (snapshot at call time). Arrays use index 0 / `length - 1`; objects use the first / last enumerable key. Empty sources collapse to key `'0'` so the chainable shape is uniform. See `firstKey` / `lastKey` near the `raf` helper.
- `patch` is built-in (not an operator): `proxy.patch([name, value, name, value, ...])` applies many child updates as **one** cascade — the backing value is updated for every pair and sinks receive a single batched `BU1` (new keys split out as `BI0`), instead of one dispatch per `proxy[name] = value`. Routes through the root resource exactly like the single-key setter (so semantics match N assignments at `receiver[name] = value`); on a sub-proxy each pair is rewritten to a deep path. For high-throughput producers that touch hundreds/thousands of rows per frame (a simulation, a market feed) this collapses the per-row dispatch fan-out to one walk per sink — see `examples/swarm/`. Dispatched in [core.ts](core.ts) alongside `connect`/`raf`/`first`/`last`. Note it still allocates one value object per changed row (the proxy dedups by reference, so pooling/mutating-in-place is skipped as a no-op) — patch saves dispatch, not allocation.
- Aggregates `sum(col?)`, `avg(col?)`, `max(col?)`, `min(col?)` return scalar ViewProxies. `col` is optional — without it, the aggregate runs over row values directly; with it, over `row[col]`. `sum`/`avg` are O(1) per delta (running total + count); `max`/`min` recompute O(n) per publish. Empty set → `undefined` (rather than `NaN` for avg / `0` for max/min). Implemented in [operators/aggregate/](operators/aggregate/).
- `tap(fn)` has two paths picked by `fn.length`: a **1+-arg** fn (`(change) => ...`) gets full change records — `{ type, key, value, at? }` with `value` `structuredClone`'d, fired once per row in a batched verb. A **0-arg** fn (`() => render()`) routes to `TapBareValue` — no clone, no record allocation, fires fn once *per emit* (one BU1/BU2/BI0 batch = one fn call). The bare path is for hot-path consumers that re-read `proxy[value]` inside their callback (chart redraws, count-textContent updates); 40%+ faster on the [tap.perf.ts](operators/tap/tap.perf.ts) batch case. Path selection is by **parameter presence**, not just `fn.length` (`tapHasParam` in [operators/tap/index.ts](operators/tap/index.ts)): a fn that declares ANY parameter — including a defaulted (`(c = {}) => …`) or destructured (`({type}) => …`) one, which both report `length 0` — takes the full record path; only a genuinely parameterless fn (`() => render()`) takes the bare path. (Source-inspecting the param list, not the arity count, is also what makes this robust to minification — a used param is never dropped.) Dispatched in [register.ts](register.ts).
- `reduce` has two arities. `reduce(fn, init)` is the general fold — non-commutative, rebuilds on every change. `reduce(add, remove, init)` is incremental: BI0/BR1/BU1 thread through `add`/`remove` in O(Δ). BU1 (a whole-slot overwrite, `data[k] = newRow`) recovers the **old** row from a per-key reference cache the operator keeps and does `remove(old)` + `add(new)`; the cache stores references (no clones), so it adds nothing to the insert-/remove-driven path. Only BU2 (a **nested** in-place edit, `data[k].f = x`) still falls back to rebuild — the row's reference is unchanged, so the cache holds the already-mutated row and there's no pre-edit value to subtract (closing that would need either a per-row snapshot, which would penalise the immutable-row crossfilter path, or an old-value protocol change). Pick the 3-arg form when (i) your fold is invertible per-row (you can write a `remove` that exactly cancels an `add`), and (ii) the workload is insert-/remove-/overwrite-driven — typically downstream of `intersect`/`between` where filter changes manifest as enter/leave events. `init` can be a value or a thunk; thunk fires on each full rebuild for folds that mutate the accumulator in place. Crossfilter-shaped "bucketed sum / running stat / top-K per group" workloads go here; `length(fn)` already handles bucketed counts incrementally so use that when counts are all you need. The 3-arg form's one footgun is an asymmetric `remove` (one that doesn't exactly invert `add` for a row), which desyncs `acc` silently — set `$.debug = true` in development to make it loud: each incremental BI0/BR1/BU1 then re-folds from scratch and `console.warn`s on the first drift (O(N) per delta, so leave it off in production; it's a dev aid, not a runtime guard).

## Adding a new operator

The canonical, full checklist lives in [operators/README.md](operators/README.md#adding-an-operator--checklist) — follow it top-to-bottom. This is a summary so you don't miss any step at a glance:

1. **Code:** `operators/<name>/index.ts` (class + factory; extend `Operator` from [core.ts:233](core.ts#L233) or `RowOperator` from [row.ts:5](row.ts#L5)); `matches(...args)` for dedup; `<name>.test.ts`; perf in **two parts (Mode A)** — a workload entry in [perf/workloads.ts](perf/workloads.ts) plus a thin `<name>.perf.ts` driver over it.
2. **Dispatch:** register in [register.ts](register.ts) (the side-effect module imported by the default `data` entry, in the `Operators[...]` block) so `proxy.<yourOp>(...)` works. `data` picks it up via `index.ts`'s `import './register.ts'`; `data/full` inherits it via `export * from './index.ts'`.
3. **Per-operator docs:** `operators/<name>/README.md` covering signatures, examples, behaviour.
4. **Catalog docs:** add the operator to [operators/README.md](operators/README.md) catalog + dispatch example, [README.md](README.md) operator table + opener blurb, and this file's `## What this is` paragraph and the dedup gotcha (if applicable).
5. **Peer benchmark (optional):** `comparisons/bench/operators/<name>.bench.ts` mirroring [comparisons/bench/operators/filter.bench.ts](comparisons/bench/operators/filter.bench.ts); then regenerate [operators/BENCHMARK.md](operators/BENCHMARK.md) + the per-op BENCHMARK files via `npm run bench:ops > /tmp/bench.md && node comparisons/bench/operators/_gen-bench-md.mjs /tmp/bench.md`.
6. **Verify & commit:** `npm test` + `npm run perf` must pass; commit per the working conventions below.

For deeper internals — the View/Sink contract, when each notification method fires, parent/child propagation — see [PROTOCOL.md](PROTOCOL.md).

> **Keep the two checklists in sync.** When the standard changes (e.g. a new doc location is added, like the recent per-op `BENCHMARK.md`), update both this summary AND the canonical list in [operators/README.md](operators/README.md#adding-an-operator--checklist) in the same change.

## Notification code legend (quick reference)

The terse method names on `Value`/`View`/`Sink` follow this scheme:

- **Prefix**: `X` = root-level (no key context); `B` = branch (operating on a sub-key).
- **Verb**: `U` = update; `I` = insert; `R` = remove.
- **Suffix digit**: depth of the key path: `0` = direct (no key, or insert position), `1` = single name, `2` = full nested path.
- **Suffix `A`**: array-aware variant carrying **splice-shift** semantics (`BR1A`/`BI0A`): a position was removed/inserted, so survivors slide and downstream array layouts must shift in lockstep.

The full set actually used: `XU0`, `XR0`, `BU1`, `BU2`, `BI0`, `BI2`, `BR1`, `BR2`, plus the array-aware `BR1A`/`BI0A`, the **positional-stable** pair `BH1`/`BF0`, and `BMV1` (the depth-1 **move** verb — a windowed sort emits it for an in-window rank rotation; `Value.BMV1`/`View.BMV1` splice + a fallback to per-position `BU1` for sinks without it, and `ArrSink`/`FunctionSink` surface it as a `{type:'move', from, to}` record). There is no `BU0`/`BR0`/`BI1` — those collapse to `XU0`/`XR0` and `BI0` respectively.

- **`BH1` (hole remove) / `BF0` (hole fill)** are the positional-stable counterparts of `BR1A`/`BI0A`. A sparse producer (`between`/`intersect`/`union`/`except`) over an **array** marks an excluded slot `undefined` *without* splicing — the array length is stable and survivors do **not** shift (so sibling sources stay index-aligned). It emits `BH1`/`BF0` so positional sinks mirror the hole/fill instead of splice-shifting. They live on `View` only; a sink that doesn't implement them falls back to `BR1`/`BI0` (correct for a position-agnostic sink like an aggregate — it just drops/adds the row). `RowOperator`, `between`/`intersect`/`union`/`except` (as consumers — each, over an **array** source, emits `BH1`/`BF0` for a membership change so a positional sink, including the `DOMSink` bound straight to it, mirrors the hole instead of splice-shifting), `group`, and `DOMSink` implement them; see [core.ts](core.ts) `View.BH1`/`BF0`, [row.ts](row.ts), [operators/between/index.ts](operators/between/index.ts), [operators/intersect/index.ts](operators/intersect/index.ts), [render/index.ts](render/index.ts).

`NU1`/`NI0`/`NR1` you'll see inside `RowOperator.loop` ([row.ts:9](row.ts#L9)) and `Value.BU1` ([core.ts:148](core.ts#L148)) are **local accumulator arrays** ("New U1 list"), not separate notification methods.

For a fuller breakdown see [PROTOCOL.md](PROTOCOL.md).

## Testing patterns

- `node:test` + `node:assert` (`deepStrictEqual` aliased as `same`, `ok`).
- Override `$.random` for deterministic IDs — see [core.test.ts:7](core.test.ts#L7).
- Capture changes with `res.connect([])`, then assert event shape `{ type: 'update'|'insert'|'remove', key, value, at? }`. See [core.test.ts:9-20](core.test.ts#L9-L20).
- Tests assert downstream views *and* their parent in the same case (e.g. [core.test.ts:134-173](core.test.ts#L134-L173) checks `res`, `res.a`, `res.a[0]`, `res.a[1]`, `res.a[2]` simultaneously).

## Performance test patterns

- Median of 5 `performance.now()` runs, threshold via `ok(elapsed < N)`. Reference: [filter.perf.ts](filter.perf.ts).
- Each `*.perf.ts` typically covers: setup cost, single-row incremental update, batch update.
- Don't widen thresholds to make a perf test pass — investigate the regression. Recent commits (`perf: incremental LimitValue with large-batch fallback`, `perf: rAF-coalesce brush input in crossfilter example`) show active perf work; respect it.
- `npm run bench:compare` runs the cross-library comparison harness in [comparisons/bench/](comparisons/bench/) (this lib vs. crossfilter / MobX / RxJS / Solid / Preact / Vue / Svelte / React) on the canonical `map → filter → top-K` workload. `npm run bench:ops` runs the **per-operator** comparison harness in [comparisons/bench/operators/](comparisons/bench/operators/), exercising each operator in isolation against the same peer set and printing one markdown table per operator plus a regressions section flagging cases where `data` isn't fastest. `BENCH_OPS=filter,map npm run bench:ops` runs a subset. Both **report**, they do not gate — peer regressions don't fail this repo's CI. The in-browser comparison demo [examples/multidim/](examples/multidim/) runs the same workload across the same nine libraries with live per-row reactive-cost trackers. The landing page ([index.html](index.html)) is now the comparison surface itself: a **single-card carousel** ([assets/race.js](assets/race.js)) that flips through nine reactive engines on one realistic order-book tick stream (depth-chart-and-ladder viz in [assets/race-views.js](assets/race-views.js)), always running `data` as a baseline so the per-frame cpu gap shows on one card. **The same carousel drives a second co-located workload**: directly below the order-book card, one inline brushing row from `examples/multidim/` for the *same* selected engine (not all nine at once) — `loadFlights()` streams the 231k-row dataset once (lazy, on scroll, determinate bar), then `mountLibRow()` mounts the selected engine's row over the cached flights; both exported from [examples/multidim/main.js](examples/multidim/main.js), styles scoped under `.race-multidim` in [assets/multidim.css](assets/multidim.css). Each engine's brushing row is **mounted once and kept alive** (toggled via `[hidden]`, not destroyed) so switching back to it stays warm — re-mounting cold made the first few brushes slow every time. No iframe, no workload toggle. Each order-book engine is defined inline in `race.js` and **settles once per frame** (not per tick) — that's what lets all nine, including the eager O(N) libs, run live at N=150k; switching engines drops the rate to a per-engine safe default. The standalone `examples/trades/` dashboard the order-book *style* came from was retired once the carousel absorbed it. Peers load from esm.sh via `index.html`'s importmap (all nine: mobx, solid, preact, vue, crossfilter2, rxjs, react/react-dom, svelte/store) — if you bump peer versions, bump them there and in `examples/multidim/`'s importmap. (The standalone `comparisons.html` + `assets/landing.css` + `assets/comparisons.css` were removed once the landing page absorbed them.) Smoke test: [tests/race.spec.ts](tests/race.spec.ts).
- Each operator owns a `BENCHMARK.md` (e.g. [operators/filter/BENCHMARK.md](operators/filter/BENCHMARK.md)) that records the latest `bench:ops` table for that operator plus a "How" section explaining why `data` wins (or what's deferred when it doesn't). **Update the BENCHMARK.md whenever you change the operator's hot path** — the numbers drift, and a stale BENCHMARK.md is worse than no BENCHMARK.md. Workflow: `BENCH_OPS=<op> npm run bench:ops`, copy the table into `operators/<op>/BENCHMARK.md`, commit alongside the code change.

## Examples

- [examples/todo/](examples/todo/) — basic mutation + filter + length.
- [examples/crossfilter/](examples/crossfilter/) — chained `between → intersect → length(group) → za → limit` over the full 231,083-row flights dataset (stream-fetched from `flights.js` with a progress bar; the `flights500.js`/`flights50000.js` files are unused smaller variants). Per-example notes in [examples/crossfilter/README.md](examples/crossfilter/README.md).
- [examples/swarm/](examples/swarm/) — a live agent-simulation control room: a SIRS epidemic over ~12k moving agents (default `?n=` overridable) at 60fps in plain JS, with a fully incremental analytics deck on `data` riding alongside. Two-tier discipline: [sim.js](examples/swarm/sim.js) owns the O(N) physics (typed-array integration, spatial-hash transmission, the canvas point cloud) and discretises position into integer `gx`/`gy` cell columns + energy bands; [main.js](examples/swarm/main.js) owns the deck — SIR counts (`pop.length(a=>a.state)`), region leaderboard (`pop.filter('state','I').length(a=>region)`), energy histogram, outbreak alarm (`regionInf.some(c=>c.value>=22)` — the `some()` boolean-aggregate graft), headline tiles (`avg`), and a brushable cohort (`pop.intersect({gx: between, gy: between})` → `.length()`/`.avg()`/`.limit(120)` rendered surgically). The bridge drains a per-frame dirty list into **one batched `pop.patch(...)`** so the operators see a single `BU1`, not one dispatch per agent. This example drove two lib changes: the `length(fn)`-rebuckets-on-`BU2` fix (the SIR/energy histograms sit directly on a mutating source) and the new `patch` built-in. ## Common gotchas

- Use `proxy[value]` (the `value` symbol), **not** `proxy.value`, to read the raw underlying data. `proxy.value` would create a child view named `"value"`.
- A `LinkedView` ([core.ts:983](core.ts#L983)) is created by **passing a proxy to `$`** — `const b = $(a)` makes `b` forward every read/write to `a`'s underlying data. **Assigning `a[value] = b` on a plain (non-linked) proxy THROWS** (`cannot set value to another data, use a linked value instead`) — that's not how you make a link. Once you HAVE a linked view, `linked[value] = otherProxy` re-points it at a new source (the documented todo/kanban `$(view)` swap, handled by `LinkedView.update`); a re-point that would form a cycle throws `cannot create a cyclic linked value`. See the `proxy/link` and `proxy/link - child propagation` tests in [core.test.ts](core.test.ts) for the full semantics.
- Operator dedup is opt-in via a `matches()` method. `between` ([operators/between/index.ts](operators/between/index.ts)), `gt`/`lt`/`gte`/`lte` ([operators/compare/index.ts](operators/compare/index.ts)), `za`/`az`/`top` ([operators/sort/index.ts](operators/sort/index.ts)), `intersect` ([operators/intersect/index.ts](operators/intersect/index.ts)), the scalar aggregates `sum`/`avg`/`max`/`min`/`some`/`every` ([operators/aggregate/index.ts](operators/aggregate/index.ts)), `distinct` ([operators/distinct/index.ts](operators/distinct/index.ts)), and `reduce` ([operators/reduce/index.ts](operators/reduce/index.ts)) implement it; repeated calls with identical args return the cached view. As of the 2026-06-11 dedup fix this covers ALL sort forms — unbounded `za('col')`/`az('col')`, numeric `top(n)`/`za(n)`, and bounded `za('col', n)` — and `between` with a reactive single-VP extent or reactive tuple bounds (matched by the bound source's view identity, not its current value). `filter`, `map`, `length`, `group`, `to`, `tap`, `union`, `except`, `keys`, `values`, `reverse` create a fresh operator on every call.
- Sinks are held via `WeakRef` ([core.ts:421](core.ts#L421)). Dropping the only strong reference unsubscribes silently. Tests keep `connect([])`'s return alive in a local for this reason.
- `between()` and similar range operators with reactive bounds (`ViewProxy` args) track their inputs reactively; with plain values they don't. `gt`/`lt`/`gte`/`lte` only take literal bounds — for a moving threshold, derive a fresh view (`src.gt('val', t[value])`) or use `between` with a reactive lo/hi.
- Pick `gt`/`lt`/`gte`/`lte` over `between(col, [T, Infinity])` when you need a single-threshold filter: same semantics, but RowOperator-based (O(1) per BU2 vs `between`'s sort-index maintenance on setup + threshold change). See [experiments/wasm/results-altbackend.md](experiments/wasm/results-altbackend.md) for the gap.
- Mutations on nested data work transparently: `res.a.b.c = 1` triggers the right notification cascade. No need for immutable updates.
- JSX `<label>{vp}</label>` routes through `.text(vp)` because there's no function sibling — preserves the host element across reactive updates. Adding a function child (`<div>{[vp, fn]}</div>` for a data binding) flips both children to the data path so `node.data = vp` and `node.fn = fn`. See the discriminator at [jsx/index.ts](jsx/index.ts) — `hasRowFn` (which excludes NodeProxy element children, so a VP with an element sibling like `<label><em/>{vp}</label>` stays on the text path and doesn't duplicate the host — fixed 2026-06-11). Don't author a single-VP child expecting iteration; use `<For>` or the `[vp, fn]` shorthand.
- **Don't mix STATIC text and REACTIVE text in one element** — `<span># {cur}</span>` renders `"general# "`, not `"# general"`. A reactive child becomes an ordered `.text()` Prop, but a static string goes through Node's SINGLE last-wins `static` slot, which is rendered AFTER all reactive children (and all but the last static string is dropped). This is a deliberate limitation of the single-`static`-slot builder design (the same `HTML.span('# ', cur)` builder call has it too; encoded in `jsx/jsx.test.ts` "only the last static wins — same for builder"). Workaround: fold the static text into the reactive value (`{cur.to(c => '# ' + c)}`) or give the static text its own element. The chat example's channel header uses the `.to()` form for exactly this reason.
- `node(...)` with a single array arg auto-spreads — see `NodeProxy.apply` in [render/index.ts](render/index.ts). So `node(<Fragment>…</Fragment>)` is equivalent to `node(...children)`. Bare arrays as the only positional arg weren't a documented builder pattern, so this was purely additive.
- A `ViewProxy` is a callable `Proxy`, so `typeof proxy.then === 'function'` — the runtime treats it as a thenable. `await proxy` (and `Promise.resolve(proxy)`, `Promise.all([...,proxy])`, returning one from an `async` fn) resolves to the current snapshot, equivalent to `proxy[value]`. This is handled by a guard in `ViewProxy.apply` ([core.ts:858](core.ts#L858)) that recognises promise assimilation by its call signature (`then` *called* with a leading function arg) and distinguishes it from genuine `.then` data access (which only *reads* the child view, never calls it) — so a key literally named `then` still works as `proxy.then[value]`. Don't rely on awaiting a proxy for async sequencing; it's synchronous snapshot sugar, not a real promise.
- `length(d => key(d))` ([operators/length/index.ts](operators/length/index.ts)) does **not** map keys to scalar counts directly. Each bucket is stored as `{ value: count }` so individual counts have their own VP identity and can be subscribed without re-rendering siblings (the crossfilter histogram-bar use case). Read the count via `counts[key].value`, not `counts[key]` — the latter is a VP for the wrapping object and stringifies to `[object Object]` (and gives `NaN` in arithmetic). `assets/demos.js` documents the trap inline above the per-tenor bars in the operator catalogue.
- `length(fn)` rebuckets on **in-place field mutations** (`data[id].col = …`, a `BU2`), not just inserts/removes: when the changed row's bucket key moves it decrements the old bucket and increments the new (creating it if it didn't exist at construction) in O(1); a field change that doesn't move the bucket republishes nothing. This was a `BU2(){}` no-op until the swarm example surfaced it — a `length(fn)` histogram over a source whose rows *mutate in place* (rather than only enter/leave via insert/remove) used to silently freeze at its construction-time buckets. A histogram downstream of `filter`/`between` already worked, because those translate a field change into `BI0`/`BR1` membership events; the gap was only `length(fn)` sitting *directly* on a mutating source. The scalar `length()` stays correctly inert on `BU2` (a field change can't change the row count).
- `group(fn)` has the **same in-place-`BU2` story** (object sources): an in-place field edit that moves a row's group key relocates the row to its new bucket (dropping an emptied group); a non-key edit forwards the deep update into the bucket so per-bucket consumers (aggregates re-projecting a column, child views) refresh. This too was a `BU2(){}` no-op until the pivot example surfaced it — a `group(fn)` over a mutating object source (e.g. a pivot whose rows' group field / measure are editable) used to silently freeze. Array-source `group` keeps the `BU2` no-op (positional rows; crossfilter never mutates rows in place). See [operators/group/index.ts](operators/group/index.ts) `BU2`.
- `between`, `intersect`, `union`, `except` build sparse arrays where excluded indices are set to **explicit `undefined`** (e.g. `view.value[name] = undefined`) rather than `delete`'d. This matters whenever **you** read the raw value: `for (i in view[value])` walks the holes as enumerable, and a `vp.to(arr => …)` that maps the array sees `undefined` rows — so densify (`vp.to(arr => arr.filter(r => r !== undefined))`, see `dense()` in `assets/demos.js`) before iterating a sparse view yourself, and format a possibly-undefined cell defensively (`r.col == null ? '–' : …`). **The `render()` DOM layer now handles sparse producers itself** (closed [ISSUES.md](ISSUES.md) C4): `DOMSink` detects a sparse array and binds nodes index-keyed (`node[k] ↔ data[k]`), maintaining them through the `BH1`/`BF0` hole protocol, so binding a `between`/`intersect`/`union`/`except` view **straight to a row template renders only the in-range rows, with no phantom holes** (both object- and array-keyed sources; `RowOperator`-based ops `filter`/`gt`/`lt`/`gte`/`lte`/`map` `delete` instead, leaving true holes for-in skips). Defensive bindings remain wise for a *different* reason: a row can go **transiently `undefined`** while it leaves a view during a multi-source re-point cascade, so `m.user.to(u => u ? u[0] : '')` guards against `undefined[0]` throwing inside the remove cascade (the library/chat gotcha) — that's a field-deref guard, not a phantom-row workaround.
- **Chaining a row op / iter op AFTER a sparse producer over an ARRAY source — FIXED (2026-06-06) via the `BH1`/`BF0` hole-vs-splice protocol signal.** `between/intersect/union/except` over an **array** source keep length stable and mark excluded slots as **positional holes**; they now emit `BH1` (hole remove) / `BF0` (hole fill) for those events instead of `BR1`/`BI0`, so downstream positional sinks mirror the hole rather than splice-shifting. `RowOperator` (`filter`/`map`), `between` (as a downstream consumer — its `XU0`/`_resort` also skip upstream holes), `group`, and **sort (`ZAValue`/`AZValue`)** implement `BH1`/`BF0`; `length(fn)` re-keys its position map on array insert/remove; `group` rebuckets array sources on an in-place key edit. As of 2026-06-06 `RowOperator.loop` also **emits** `BH1`/`BF0` (not `BR1`/`BI0`) when `filter`/`gt`/`lt`/… flips a row's membership over an **array** source — a predicate flip fills/holes a slot in place (no splice), so a positional sink (notably a windowed sort) must mirror the hole; sinks without `BH1`/`BF0` (aggregates, `length`) fall back to `BR1`/`BI0` unchanged (the `DOMSink` now implements them — see C4 below). The previously-documented ghost rows (`between(arr).filter(fn)` after a bound move) and `Cannot read 'col'` crashes (`filter(arr).between(...)`) are gone — verified by the differential harness ([differential.test.ts](differential.test.ts), `between→filter/map/az`, `filter→between`, `group`, `between→group`, `length-fn` all green for array sources). Object-keyed sources remain the simplest choice, but array-source sparse chains are now correct at the **data** layer. (The *render* layer also handles a sparse producer bound directly to a row template now — `DOMSink` binds index-keyed and tracks holes via `BH1`/`BF0`, closing [ISSUES.md](ISSUES.md) C4; see the sparse-render gotcha above.)
- **`map`/`filter` after a *windowed* sort (`az`/`za`/`top`/`limit`) — FIXED (2026-06-06) via `RowOperator.BI0A`.** A row entering the window arrives as a positional `BI0A([rank, row])` (preceded by a `BR1A` evicting the row that fell out); `RowOperator.BI0A` now splices in lockstep (mirroring its `BR1`) instead of letting `loop` misclassify the insert as an update and drop the displaced row. `length`/`sum`/aggregates after a window were already fine.
- **Chained *windowed* sort (`za(col,n).az(col,n)`) — FIXED (2026-06-06) via content-stable rotation emission.** A bounded window rotation (a row crosses the window boundary while the window stays full) used to be emitted as a **mid-window** `BR1A`(evict) + `BI0A`(insert) pair; the interior splice plus the inconsistent intermediate window state (between the two events) corrupted a downstream positional sort's position→rank map — ghosts, dupes, stale order. A full-window rotation only ever changes *content* at fixed positions, so `ZAValue._window()` now reconciles it as content-stable `BU1`s (plus a **tail-only** `BR1A`/`BI0A` for a genuine size change) — the single-row generalisation of the `_batchRemove`/`_batchInsert` reconcile. Tail splices and `BU1`s compose correctly through a downstream sort; mid-window splices don't. The `BU1` cases 2/3, the bounded `BI0` full-window insert, and the bounded `BR1`/`BR1A` in-window removal all route through `_window()`. **Consequence for change-stream consumers:** a single-row window rotation now emits `update`s, not a `remove`+`insert` pair (and a child view at a rotated slot no longer flashes to `undefined`) — matching what the batch-window path already did; `index.test.ts`'s `za` change-stream was updated to match. Unbounded sorts keep genuine mid-array splices. In-window rank shuffles still emit a single `BMV1` move. Verified across the chained-sort family (`za-window→az-window`, `az-window→za-window`, `za-window→za-window`, `za→az` unbounded, `za-window→az-window→map`, `filter→za-window→az-window`) in [differential.test.ts](differential.test.ts). Two latent bugs fell out of this and were fixed alongside: **(a) `AZValue.XU0` never set `this.isArr`**, so an *ascending* sort over an array (or an array-emitting parent like an unbounded `za`) skipped the `BI0`/`BR1A` index-shift bookkeeping and mis-tracked positions on a mid-array insert/remove (masked because the harness only ever appended at the tail); **(b) `filter`'s predicate-flip path over an array** filled/holed a slot in place but emitted splice-semantics `BI0`/`BR1`, so a downstream windowed sort shift-spliced on a hole fill — now `RowOperator.loop` emits `BF0`/`BH1` for array predicate flips and `ZAValue` implements `BF0`/`BH1` (rank in/out with no index shift). The phantom-DOM `"-1"`-key symptom stays fixed by the `oidx >= 0` guard.
- **`length(fn)` keeps emptied buckets as `{ value: 0 }` (intentional, fixed-keyspace persistence).** When a bucket's last row leaves it is NOT pruned — the bucket stays at `{ value: 0 }` so a histogram with a known category set keeps showing a stable (zero-height) bar rather than a bar vanishing/reappearing, and reads like `counts[k].value` / `counts[k]?.value || 0` stay valid (the swarm/demos/kanban/chat examples and `operators/length/length.test.ts` all rely on this). The consequence: chaining an **enumerating** op onto `length(fn)` — `keys()`/`values()`/`length()`/`limit()` over the bucket map, or "list the live categories" — will include the zero-count buckets. Filter them (`> 0`) or read by known key; don't treat `length(fn).keys()` as "currently non-empty categories". This is a deliberate contract, not a bug; `group(fn)` (which DOES prune emptied buckets) is the alternative when you want enter/leave semantics.
- **`limit(n)` over an OBJECT source is iteration-order-loose (history-dependent), like `distinct`.** `limit` keeps "the first `n` non-undefined entries in **source iteration order**." For an **array** that order is stable (positions), so `limit` is deterministic and the array `limit` paths are fully incremental + correct (the `BR1A`/`BI0A`/`BMV1` recompute handles a re-ordering sort parent — DECISIONS C10; the array `BI0` dedups hole-fills so a sideways brush can't duplicate — C11). For an **object**, iteration order is *not* semantically meaningful and **drifts under mutation**: a key deleted then re-added (exactly what `between`/`intersect` do to an object's `view.value` when a row leaves then re-enters on a brush) moves to the **end** of iteration order. So `obj.between(...).limit(n)` brushed back and forth can pick a *different set* of `n` rows than a from-scratch rebuild — both are valid "first n in iteration order" of their (legally different) orderings. This is the same history-dependence `distinct` has; the differential harness normalizes `distinct` to a keyset for the same reason. If you need a **stable** top-n over an object, sort first (`obj.az('col').limit(n)` / use a bounded `za('col', n)`) or key the source so iteration order is stable. Don't treat `obj-source.limit(n)` as a deterministic set.
- **Set-algebra producers (`intersect`/`union`/`except`) over an ARRAY source under insert/remove churn — FIXED (2026-06-08), C12 closed.** The array half was a C1-family array-positional gap: an array remove shifts later indices, but these operators handled removes with the OBJECT path (`delete`/hole, no splice), so their per-index bitmask + sparse `view.value` drifted from the shifting source (a ghost row accumulated / a drifted survivor got deleted), and a tail insert excluded by a secondary facet was wrongly admitted (the secondary's positional `BI0A` carries `undefined` for an excluded slot — a hole, not membership — but the object `_enter` set the bit anyway). **All three now have array-only `BI0A`/`BR1A` handlers** ([operators/intersect/index.ts](operators/intersect/index.ts), [operators/union/index.ts](operators/union/index.ts), [operators/except/index.ts](operators/except/index.ts)): a structural remove splices only on the PRIMARY echo (`v === this.p`, the canonical index identity), routing a secondary's removal to the by-name membership path (no shift); a tail insert grows the slot naturally and folds each source's membership in from its carried value (a hole clears the bit / excludes). Order-independent, no cross-source length compare (a filter facet's trailing holes make its `.length` unreliable). NB **union's primary echoes FIRST** (its `p` is itself a derived facet) where intersect/except's echoes LAST — the primary-identity keying is order-independent so both work; and **union/except read the echo's CARRIED value, not a positional `_pick`/`other.value[at]` re-read**. See [DECISIONS.md → C12 (array half — intersect/union/except)](DECISIONS.md). The differential harness runs every set-algebra scenario, array and object, under the widened mutation vocabulary. **(2026-06-11 re-examination) further set-algebra fixes**: `between` marks `sorted` dirty when relaying mutations while unfiltered (full-domain alias — the crossfilter reset state — no longer leaves a stale `sorted` for the next brush); `between`'s reactive single-VP-extent dedup now matches (by underlying-view identity); the primary `BR1A` of intersect/union/except always emits the positional splice even for a holed slot (downstream positional consumers stay aligned); `except` admits a tail insert on the primary echo (so a `between`/`intersect` `other` that doesn't echo an out-of-range insert no longer drops an admissible row); and `intersect` dedups duplicate/self sources (`a.intersect(a)`/`a.intersect(b,b)` were silently empty). **C13 is now closed** — `RowOperator` arrays mirror source length, so a filter facet with trailing-excluded rows is no longer index-misaligned. **(2026-06-13) C15 is now closed too** — the deepest array-positional corner (`between`/`intersect`/`union`/`except` over arrays desyncing under COMBINED mid-insert + patch-batch + slot-clear + brush churn, the 9 differential `KNOWN_FAILURES`). One unifying root cause: these producers were never made conformant to the array-positional INSERT half of the contract (C13 had fixed only `RowOperator`). Fixes: `between.XU0` pads its sparse array to source length + `between.BI0` always forwards the positional insert (hole for an out-of-range row); `intersect`/`union`/`except.BI0A` splice a fresh cell on a MID-array insert (gated on `pendingShift = p.value.length > filters.length`, so tail/C12 paths are unchanged) and forward the mid-insert hole downstream; `ZAValue.BI0` and `group.BI0A` guard a carried-undefined hole (shift positions, don't rank/bucket it); `intersect._enter` dedups the object double-insert; `union` drops reference-dedup so it emits in-place edits downstream (a shared-reference facet move was swallowed). `KNOWN_FAILURES` is empty; verified by 18,600 fresh-seed stress runs over the set-algebra→sort/aggregate compositions. See [DECISIONS.md → C15](DECISIONS.md). **One residual remains** ([C16](ISSUES.md)): `intersect` with a SPARSE producer (`between`) as its PRIMARY over an array drops a survivor on a remove (intersect's `_leave`-on-secondary-BR1A supports the C14 independent-array case; no-opping it would break C14, and between-as-intersect-PRIMARY is itself not shipped — the crossfilter pattern is a RAW primary with between/filter SECONDARIES, which is correct). Workaround: raw-primary intersect or object keys. (The other probe residual — `union→sort` under a facet-MOVING `patch-batch` — was fixed: `union._enter` emits re-rank `BU1`s before insert `BF0`/`BI0` so a downstream sort stays monotonic for the insert bisect.) The other remaining set-algebra limitation is **[C14](ISSUES.md)**: `intersect` over INDEPENDENT (not derived, not object-keyed) ARRAY sources doesn't admit a tail insert — use object-keyed or derived sources (still the right default for high-churn set-algebra anyway).

## Working conventions in this repo (please follow)

- **Keep docs in sync with code.** When you change behavior, the public API, commands, or conventions, update the relevant docs in the *same* change:
  - `CLAUDE.md` for Claude-facing notes (this file).
  - [PROTOCOL.md](PROTOCOL.md) — the canonical reference for internals (notification codes, View/Sink contracts, propagation rules). `.claude/architecture.md` is now just a pointer to it.
  - [README.md](README.md) for human-facing usage and API examples.
  
  If you add or remove an operator, update the dispatch description and gotchas here, the legend (if it touches notification codes) in `PROTOCOL.md` (and the quick-reference subset in this file), and the examples in `README.md`. Stale docs mislead future sessions — assume someone will trust them.

- **Commit granularly with detailed messages.** One logical change per commit (one bug fix, one perf improvement, one doc update — *not* bundled). Follow the existing style visible in `git log`: Conventional-Commits-ish prefixes like `fix(core): ...`, `perf: ...`, `fix(examples/todo): ...`, `docs: ...`. Each message body should explain *why* the change is needed and *what* its visible or internal effect is — not just restate the diff. Commit immediately after each logical change rather than batching at the end of a session, so a partial revert is always possible.

- **Before committing, present the change for review.** Don't commit silently. For each logical change, surface to the user (in chat):
  1. **What changed** — a brief plain-language summary of the diff: which files, which functions/sections, the user-visible or internal effect. For non-trivial code, include the diff itself or the key hunks.
  2. **Why** — the motivation (bug being fixed, regression being prevented, refactor rationale, perf hypothesis).
  3. **Test results** — the relevant tail of `npm test` output (pass count + any test names you added). For bug fixes, name the regression test you added.
  4. **Perf results** — for code changes, the relevant `npm run perf` numbers, ideally with a before/after comparison if you have it. For doc-only changes, state explicitly that perf is N/A and why.
  5. **Anything else relevant** — e.g. a known limitation, a follow-up TODO, a file you intentionally left out of the commit, an unrelated working-tree change you did *not* stage.

  Then commit. The user should never have to read the diff after the fact to understand what landed. Skipping this step also skips the chance to catch a problem before it's in history.

- **Run tests on every change. Extend them if the existing suite doesn't cover the change.** Before committing any code change, run `npm test` and confirm all 62+ tests pass. If your change adds or modifies behavior that isn't already exercised — a new operator, a new branch in an existing operator, a fixed bug, a new edge case — add a test for it in the corresponding `*.test.ts` file. The recently added `proxy/link - child propagation` test in [core.test.ts](core.test.ts) is a good template: it documents *why* the test exists (which regression it catches) in a comment, and asserts both the data shape *and* the change-event stream. A bug fix without a regression test invites the same bug to come back.

- **Run perf tests on every change. Watch for regressions; extend the suite if the change has a new perf surface.** Before committing, run `npm run perf` and confirm all assertions pass *and* the printed timings haven't drifted upward versus what `git log` and the existing thresholds suggest. The thresholds in `*.perf.ts` are guard rails — a change that only just squeaks under one is suspicious. If your change introduces a new hot path or a new operator, add corresponding setup / single-update / batch-update cases — under Mode A that means adding a `{ gate, run, batch?, reps?, keep? }` case to the operator's entry in [perf/workloads.ts](perf/workloads.ts) (the gate driver picks it up automatically and the report re-measures it); a brand-new operator adds an export there plus a thin driver `operators/<op>/<op>.perf.ts` following [filter.perf.ts](operators/filter/filter.perf.ts). Don't widen thresholds to make a failing perf test pass — investigate the regression instead.

- **Don't undo recent perf work.** Before refactoring `sort.ts` (`LimitValue`), `core.ts` (`LinkedView` propagation), or the crossfilter example's brush handling, check `git log` for recent `perf:` / `fix(core):` commits and understand what they were optimizing.
