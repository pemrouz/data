comparisons

How data lines up against crossfilter, MobX, RxJS, React, and the modern signal libraries (Solid, Preact, Vue, Svelte).

This page isn't a "we win" page. The reactive landscape is wide; each library optimises for a different shape. The aim here is to make the shape differences visible — model, mutation API, where work actually happens — and then back the discussion with reproducible numbers from a single workload run across every library.

Want to feel the difference rather than read about it? examples/multidim rebuilds the crossfilter brushable-charts demo once per library against the same 231,083 flight records, with live brush latency captured per row.

benchmark — trades streaming through map → filter → top 10

Headline. On the 3-view dashboard — the realistic case — data finishes 1,000 ticks in ~12 ms; every peer is between 24× and 245× behind: Preact 24×, crossfilter 33×, Solid 43×, MobX 110×, svelte/store 173×, React 202×, RxJS 205×, Vue 245×. Adding two more derived views to data's graph cost essentially nothing (11.79 → 12.17 ms) — one tick propagates through one path that fans out to all three views. For the signal libraries, adding two views roughly doubled the per-tick cost (Preact 174 → 287 ms, Solid 156 → 521 ms, Vue 1,373 → 2,983 ms): each new view is a new computed that walks the full source on every change. React's whole-component re-render hits every useMemo on every tick — the dep arrays save nothing once the array reference changes.

Three-stage pipeline run identically against every library on a workload designed to look like a real reactive UI (a blotter, a leaderboard, a live list). 10,000 trades of { id, bid, ask }; derived view = the top 10 trades by spread = ask − bid, filtered to spreads above a threshold (~50% of rows qualify).

A tick is one mutation of one row's bid or ask. Three cases: single (one tick + read), top view (1000 sequential ticks, each settling the top-K view), and 3-view dashboard (1000 sequential ticks, each settling three independent views off the same source — count, top-10, and a running average). The dashboard case is what real reactive UIs look like: a single source feeds many derived views, all of which need to stay in sync after every mutation.

Median-of-5 wall-clock with one warmup discarded; global.gc() between reps. The derived count is read inside each measured region so libraries with lazy/scheduled flush actually settle. Numbers from npm run bench:compare; refresh after dependency bumps.

Each peer's pipeline is split into three chained reactive nodes — a withSpread stage, a filtered stage, a top stage — mirroring data's map → filter → za chain rather than fusing everything into one big computed body. This is what real pipelines look like as they grow (different consumers wanting different points along the chain), and it's the encoding the side-by-side code below shows. RxJS and React replace the array on every tick; crossfilter mutates via remove + add; MobX/Vue mutate in place; MobX wraps each tick in runInAction. Svelte uses svelte/store — runes need the compiler and aren't headless-bench friendly. No library uses a whole-stream batching primitive: that would amortize 1000 ticks into one settle, which a real tick-driven UI can't do.

scaling — does the per-tick cost grow with N?

Same workload, dataset doubled to 20,000 trades. Still 1,000 ticks, still three derived views (count + top-10 + running average). The question is whether each library's per-tick cost grows with the collection size or stays close to constant.

library dashboard @ 10k (ms) dashboard @ 20k (ms) ratio (20k / 10k) notes
data 12.1718.461.52× per-tick cost ~constant; setup grows linearly with N — the cost we pay scales with changes, not collection size
preact-signals 286.88152.660.53× faster at 20k — with sparser ticks (1000 hits over 20k rows vs. 10k), per-row signal invalidations stay bounded and fewer downstream views recompute
solid 520.60304.430.58× same workload-shape effect as preact: per-row signals + reference-equality dedup absorb sparser ticks well
mobx 1,343.55766.080.57× same shape effect — fewer rows actually trigger recomputation; computed can dedup unchanged outputs
vue-reactivity 2,983.122,685.490.90× about flat — proxy bookkeeping is the constant tax; computed bodies still walk the full collection
rxjs 2,498.054,988.502.00× linear scaling — every .next() rebuilds the full pipeline output regardless of which row changed
react 2,455.685,289.562.15× linear scaling — every render walks the full chain (map+filter+sort) regardless of which row changed
svelte (store) 2,110.875,204.582.46× linear scaling — array-replace per .update, every derived reruns over the full collection
crossfilter 405.391,665.674.11× super-linear — remove + add rebuilds parts of the dimension index on every tick; the per-tick index work grows worse than linearly with N

Two things to read out of this table. First, data's per-tick cost is essentially flat — going from 10k to 20k rows adds 6 ms total across 1,000 ticks (~6 µs per tick). That's the structural promise of a path-based reactive graph: cost scales with what changed, not with the size of what stayed the same. Second, the peers split into two camps. Signal libraries (preact, solid, mobx) actually got faster because the workload itself becomes sparser — 1,000 ticks distributed over 20k rows means each row gets touched less, and per-row signal invalidations short-circuit more often. The bulk-replace libraries (rxjs, react, svelte/store) and crossfilter's index-rebuild scale linearly or worse — every tick rebuilds work proportional to N. At 20k rows the gap between data and the slowest peers is ~280×; at 100k+ rows the gap to the bulk-replace camp would keep widening, while the gap to the signal libraries would compress further (their workload-sparseness advantage tops out once per-row signal allocation cost dominates).

per-library detail

crossfilter — the only other library with native incremental top-K

Crossfilter is the original brushable-dimensions library, and the one peer with a native incremental top-K: dim.top(K) walks the sorted dimension index until it has K records. On a fixed dataset it's hard to beat. The wedge between the two libraries is editability: crossfilter has no in-place mutation. Each tick is a cf.remove(predicate) + cf.add(newRow) round-trip, both of which update the dimension index. data mutates through the proxy and routes one path through map → filter → za — O(1) + O(1) + O(log N) bisect on its sorted index.

data
import { $, value } from 'data/full'

const trades = $(makeTrades())
const top = trades
  .map(t => ({ ...t, spread: t.ask - t.bid }))
  .filter(t => t.spread > THRESHOLD)
  .za('spread', 10)

trades[42].bid = 99.5
const rows = top[value]    // top 10 by spread desc
crossfilter2
import crossfilter from 'crossfilter2'

const cf      = crossfilter(state)
const dSpread = cf.dimension(d => d.ask - d.bid)
dSpread.filterRange([THRESHOLD, Infinity])

cf.remove(d => d.id === 42)
state[42] = { ...state[42], bid: 99.5 }
cf.add([state[42]])        // remove + add
const rows = dSpread.top(10)

Single tick: data ~0.20 ms vs. crossfilter ~0.71 ms — ~3.6× faster. 1000-tick stream: ~12 ms vs. ~286 ms — ~24× faster. Both libraries have incremental top-K, so the gap is smaller than against the bulk-replace peers; the remaining gap is crossfilter's mandatory remove + add per tick (the spread index is updated twice). For a static dataset with brushable filters, crossfilter is still the right tool; for a continuously editing dataset, data wins by a clear order of magnitude.

mobx — closest API analogue: proxy-based reactive state

MobX shares data's proxy-based mutation feel (trades[i].bid = … Just Works), and its computed dedups recomputes when reads don't change. The friction is structural: there's no za/top, no incremental sorted index. The whole derivation lives in one computed body that filters + sorts + slices the entire collection on every recomputation — O(N log N) per tick. Wrapping each row in observable.object also pays a per-row tax that shows up in the setup column.

data
import { $, value } from 'data/full'

const trades    = $(makeTrades())
const withSpread = trades.map(t =>
  ({ ...t, spread: t.ask - t.bid }))
const filtered   = withSpread.filter(t =>
  t.spread > THRESHOLD)
const top        = filtered.za('spread', 10)

trades[42].bid = 99.5
const rows = top[value]
mobx
import { observable, computed, runInAction } from 'mobx'

const trades = observable.array(
  makeTrades().map(t => observable.object(t)))

const withSpread = computed(() =>
  trades.map(t => ({ ...t, spread: t.ask - t.bid })))
const filtered = computed(() =>
  withSpread.get().filter(t => t.spread > THRESHOLD))
const top = computed(() =>
  [...filtered.get()].sort((a, b) => b.spread - a.spread)
                     .slice(0, 10))

runInAction(() => { trades[42].bid = 99.5 })
const rows = top.get()      // 3× O(N) walks

Setup: ~147 ms for MobX (10k observable.object's) vs. ~11 ms for data. Single tick: ~16.5 ms vs. ~0.20 ms — ~80× — because every change triggers a full re-walk through three chained computeds. 1000-tick stream: ~525 ms vs. ~12 ms — ~45×. MobX is fine for in-place mutation of small reactive state; for continuous ticks over thousands of rows with multiple chained derived views, the per-tick re-sort dominates.

rxjs — stream composition, not collection reactivity

RxJS is built around streams of values, not reactive collections. The natural shape here is a BehaviorSubject<Trade[]> piped through map — every .next() reruns the full pipeline (filter + sort + slice) over a freshly substituted array. There's no per-row reactivity, no incremental aggregation, no incremental sort. RxJS optimises for stream composition (combine, throttle, debounce, switchMap), not point-update efficiency over a collection.

data
import { $, value } from 'data/full'

const trades    = $(makeTrades())
const withSpread = trades.map(t =>
  ({ ...t, spread: t.ask - t.bid }))
const filtered   = withSpread.filter(t =>
  t.spread > THRESHOLD)
const top        = filtered.za('spread', 10)

trades[42].bid = 99.5
const rows = top[value]
rxjs
import { BehaviorSubject } from 'rxjs'
import { map } from 'rxjs/operators'

const subject = new BehaviorSubject(makeTrades())
const withSpread$ = subject.pipe(map(rows =>
  rows.map(t => ({ ...t, spread: t.ask - t.bid }))))
const filtered$   = withSpread$.pipe(map(rows =>
  rows.filter(t => t.spread > THRESHOLD)))
const top$        = filtered$.pipe(map(rows =>
  [...rows].sort((a, b) => b.spread - a.spread)
           .slice(0, 10)))

let last = []
top$.subscribe(v => last = v)

const next = subject.value.slice()
next[42] = { ...next[42], bid: 99.5 }
subject.next(next)       // 3 stages, all re-run

Single tick: data ~0.20 ms vs. RxJS ~6 ms — ~30×. 1000-tick stream: data ~12 ms vs. RxJS ~3,400 ms — ~280×. Each tick is its own emission and each emission re-runs all three pipe stages over the full collection; the cost compounds badly when the derivation is non-trivial. RxJS is still the right tool for actual streams (event composition, temporal operators); it's the wrong shape for editable collections with sorted views.

react — component-render reactivity, not graph reactivity

React's reactivity lives at the component level: state changes re-render the whole component, and useMemo skips work when its dependency array is reference-equal to the previous render. The idiomatic shape for an editable list is one useState<Trade[]> at the top, then chained useMemos for each derived stage. Each tick replaces the array reference (immutable update), so every useMemo in the chain re-runs from scratch on every render — the dep arrays don't save anything once you've replaced the parent.

There's no per-row reactivity, no incremental sorted index, no fine-grained dependency tracking the way Solid or Preact have. Conversely, React is a full UI framework; the others in this column are reactivity primitives. The benchmark uses react-test-renderer so the same hooks runtime runs as in react-dom — what's measured is the hooks + useMemo dep-tracking layer, not reconciliation against real DOM.

data
import { $, value } from 'data/full'

const trades     = $(makeTrades())
const withSpread = trades.map(t =>
  ({ ...t, spread: t.ask - t.bid }))
const filtered   = withSpread.filter(t =>
  t.spread > THRESHOLD)
const top        = filtered.za('spread', 10)

trades[42].bid = 99.5     // path: 1 row through map,
                          // 1 row through filter,
                          // O(log N) bisect
const rows = top[value]
react (hooks)
import { useState, useMemo } from 'react'

function App() {
  const [trades, setTrades] = useState(makeTrades)
  const withSpread = useMemo(() =>
    trades.map(t => ({ ...t, spread: t.ask - t.bid })),
    [trades])
  const filtered = useMemo(() =>
    withSpread.filter(t => t.spread > THRESHOLD),
    [withSpread])
  const top = useMemo(() =>
    [...filtered].sort((a, b) => b.spread - a.spread)
                 .slice(0, 10),
    [filtered])
  // tick:
  setTrades(prev => {
    const next = prev.slice()
    next[42] = { ...next[42], bid: 99.5 }
    return next
  })  // re-renders, re-runs all 3 useMemos
}

Single tick: data ~0.20 ms vs. React ~3.9 ms — ~20×. 1000-tick stream: data ~12 ms vs. React ~2,206 ms — ~187×. The same shape as RxJS — every tick re-runs the full chain — but with React's render scheduling, scheduler bookkeeping, and Hook invocation overhead on top. 3-view dashboard hits ~2,456 ms; adding two more useMemos did very little because the existing chain already dominated. React is the right tool for component-driven UI with modestly-sized state; it's the wrong shape for thousands of rows mutating per tick.

signals — solid, preact, vue, svelte

The modern signal libraries — Solid's createSignal, Preact's @preact/signals-core, Vue's ref/reactive, and Svelte 5's runes — all share a core insight: track reads at the signal level, re-run only the consumers of changed signals. The competitive shape here is a per-row signal for each mutable field (bid, ask); the memo aggregates over all rows but only the changed signals appear in the dep graph for invalidation.

These are primitives, not collection libraries. There's no incremental filter, no incremental sorted index. The whole derivation lives in one memo body that filters, sorts, and slices the full 10k rows on every recomputation — O(N log N) per tick. The advantage over MobX is that per-row signals cost less to create than per-row observable.object.

Svelte note: data's benchmark uses svelte/store (writable + derived), which is plain runtime. Svelte 5's $state/$derived runes need the Svelte compiler and a component context, neither of which fits a headless node --test bench. In practice runes track at the signal level like the others above.

Solid note: solid-js's node export condition resolves to a SSR build whose signals are inert (no reactive propagation) — a real footgun for headless benchmarking. The bench imports solid-js/dist/solid.js explicitly to get the runtime build, so the numbers reflect Solid's actual reactive system.

                         // filter → 1 row,

solid (representative)
import { createSignal, createMemo, createRoot }
  from 'solid-js/dist/solid.js'

const cells = makeTrades().map(t => {
  const [bid, setBid] = createSignal(t.bid)
  const [ask, setAsk] = createSignal(t.ask)
  return { id: t.id, bid, setBid, ask, setAsk }
})
const top = createRoot(() => {
  const withSpread = createMemo(() =>
    cells.map(c => ({ id: c.id,
                      spread: c.ask() - c.bid() })))
  const filtered = createMemo(() =>
    withSpread().filter(t => t.spread > THRESHOLD))
  return createMemo(() =>
    [...filtered()].sort((a, b) => b.spread - a.spread)
                   .slice(0, 10))
})

cells[42].setBid(99.5)
const rows = top()       // 3 memos, full sort on read

Solid: single ~7.2 ms, stream ~156 ms (~36× and ~13× behind data). Preact: single ~7.1 ms, stream ~174 ms (~36× and ~15× behind). Svelte/store: single ~4.7 ms, stream ~2,134 ms (~180× behind — the array-replace + sort + slice per .update is brutal at this scale). Vue: see caveat below. On every case data wins decisively. The reason isn't memo scheduling — Solid and Preact have lean schedulers — it's that each memo body has to sort the filtered collection on every recomputation, and there's no way to make that incremental in a primitives library.

Vue caveat (~1,373 ms on the stream). reactive(rows) deep-proxies every row; each trades[i].bid = … goes through scheduler bookkeeping, and three chained computeds re-run on each .value read (map, filter, sort+slice). In a real Vue app you'd reach for shallowReactive, markRaw, or simply not put 10,000 reactive rows in component state. The number reflects the natural Vue shape for this workload — an honest figure for the comparison, not a refutation of Vue for the kinds of state Vue is actually used for.

where data isn't the right tool

  • You need a full UI framework. Solid and Svelte ship with everything (router, transitions, server-side rendering); data's render layer is intentionally minimal.
  • You're composing async event streams. RxJS is the right tool — debounce/throttle/combineLatest/switchMap exist for a reason. data stays in the synchronous, point-update lane.
  • You want a static dimensional analytics index over a fixed dataset. Crossfilter's groupAll().reduceSum/Count over precomputed dimensions wins on raw query throughput when the data doesn't change.
  • You're already inside a Vue/React/Svelte/Solid component tree. Use the framework's reactivity — adding data on top adds a second graph for no gain. data is most useful when you don't have a framework's reactivity already.
